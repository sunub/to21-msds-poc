# version1 ~ version12 추출 방법 전체 정리

`data/pages/version*`가 각각 어떤 코드로, 어떤 방법으로 만들어졌는지 한 번에 정리한다.

> **⚠️ version10은 영구 결번이다.** B에게 공유한 클라우드 드라이브에 이미 `version10.zip`이라는 파일이 실제로 존재하고, 그 안의 내용은 **version3**(Qwen3-VL-4B 대조 전사)이다. 즉 "version10"이라는 번호는 이미 외부에 나가서 의미가 고정돼 있으므로, 로컬 코드/데이터에서는 **다시는 이 번호를 재사용하지 않는다.** 그래서 Docling 단독 추출은 version11, 하이브리드는 version12로 번호를 매겼다(둘 사이에 공백 없이 9 다음 11로 건너뜀).

> **커밋 관련 참고**: `data/pages/*`는 `.gitignore`로 전부 제외돼 있어(D-47) 산출물 폴더 자체는 git에 올라가지 않는다. 커밋되는 건 이 결과들을 만든 **코드 파일**(`backend/scripts/*.py`, `backend/src/...`)뿐이다.

## 버전별 상세

### version1 — PDF 텍스트 + 이미지 렌더링 (OCR 별도 파일)
PyMuPDF로 페이지별 텍스트(`pNNN.txt`)와 200DPI 이미지(`pNNN.png`)를 뽑고, 텍스트층이 나쁜 페이지는 `ocr_paddle.py`가 따로 PaddleOCR을 돌려 `pNNN_ocr.txt`라는 별개 파일로 저장(하나로 합치지 않음). **B에게 `C(전처리)`로 전달한 것도 바로 이 version1 결과에 `write_metadata.py`(metadata.json)와 `build_combined_md.py`(combined_v2.md) 2개 파일만 추가한 것**(diff로 바이트까지 동일함을 확인).

### version2 — PDF 텍스트 + PaddleOCR 하이브리드 (기준 방법)
PDF 좌표 텍스트를 신뢰도 1.0으로 우선 쓰고, 안 겹치는 PaddleOCR 결과만 추가. `pipe_rows`(표 `|` 묶기), `line_numbers`(`L001`) 옵션이 있지만 기본값은 둘 다 꺼짐 — version2/version7은 이 기본값 그대로 실행된 것.

### version3 — VLM(Qwen3-VL-4B) 대조 전사 + 그림문자 전용 판독
이미지, PDF 텍스트 후보, Paddle 후보를 한 프롬프트에 넣고 Qwen에게 "이미지를 기준으로 최종 원문을 결정"하게 함. 추가로 **그림문자(GHS 픽토그램)·신호어** 전용 로직이 있음:
- 참고 텍스트에 "그림문자"/"pictogram" 단어가 있는 페이지에서만 별도로 Qwen을 한 번 더 호출(`PICTOGRAM_PROMPT`).
- GHS01(폭발)~GHS09(환경유해성) 대응표를 프롬프트에 명시, 그림문자 개수·순서·신호어를 `[그림문자 N개: GHSxx, GHSxx]` / `[신호어: 위험/경고/없음]` 형식으로 판독.
- 결과는 본문 전사 뒤에 `[그림문자·신호어 전용 판독]` 섹션으로 덧붙여짐 — 같은 이미지를 본문 전사(1차) + 그림문자 전용(2차), 두 번 모델에 넣는 구조.
- **B에게는 "version3.zip"으로, 그리고 드라이브에는 `version10.zip`이라는 이름으로도 전달됨** (같은 내용, 이름만 다름).

### version4 — C 역할 후처리 (섹션 분할 + 코드 추출 + 표 묶기)
**`run_c_preprocess.py`**가 실제 생성 코드다(⚠️ 이전에 `ocr_batch_version4.py`라고 잘못 안내한 적 있어 정정). version2 결과를 입력으로 받아 `msds.preprocess.c_pipeline.process_document()`로:
- 16개 statutory 섹션 분할, 다중 MSDS 문서 경계 판별
- H/P코드·CAS·UN번호 추출
- 좌표 기반 표 행 묶기

B 전달용 `version4`(표만 `|`로 묶인 txt)와, 분석 근거(sections/codes/table_rows/diagnostics.json, report.md)가 담긴 `version4_analysis`를 함께 만든다.

### version5 — C→B 전달 규격 포장
`build_c_to_b_contract.py` 기본 인자(`--source-root version4`). 새로 OCR을 돌리지 않고 version4의 좌표 결과를 재사용해 `data/pages·sections·codes/version5`라는 최종 규격으로 재작성.

### version6 — 재OCR(묶기+줄번호) + 재포장
`ocr_batch_version6.py`가 version2 로직에 `pipe_rows=True`,`line_numbers=True`를 고정해 처음부터 다시 OCR(`version6_ocr`), `build_c_to_b_contract.py --source-root version6_ocr`가 같은 포장 로직을 적용해 `version6` 생성.

### version7 — version2 재현성 확인
별도 스크립트 없이 `ocr_batch_version2.main(output_version="version7")`을 그대로 호출(옵션 전부 기본값). "지금 코드로 다시 돌리면 같은 결과가 나오는가"를 확인한 재실행.

### version8 / version9 — 같은 스크립트, 다른 실행 범위
`ocr_batch_version8.py` **하나**가 `--output-version` 인자로 출력 폴더만 바꿔서 둘 다 만든다.

```python
parser.add_argument("--output-version", default="version8", help="출력 폴더 이름 (예: version9)")
...
return run_extractor(output_version=args.output_version, pipe_rows=True, line_numbers=True, ...)
```

- `python ocr_batch_version8.py` → `version8`(처음엔 T21-025 등 일부 문서로 "표 묶기 고침" 테스트)
- `python ocr_batch_version8.py --output-version version9 --force` → `version9`(방법이 맞다고 확인된 뒤 manifest 20개 문서 전체로 확장)

방법은 완전히 동일, 차이는 **대상 문서 범위**뿐. 커밋 히스토리도 같은 파일 하나가 두 번 수정된 것으로 남아있다(`77ec03b`에서 최초 작성, `cea7208`에서 `line_numbers`/`--output-version` 추가).

### version10 — 영구 결번
처음엔 Docling 결과를 "version10"으로 부르려 했으나, **B에게 공유한 드라이브에 이미 `version10.zip`(=version3) 파일이 실제로 존재**함이 뒤늦게 확인됐다. 번호를 한 칸씩 당겨 공백을 메우려는 시도도 해봤지만, 외부에 이미 나간 번호와 겹치는 위험이 더 크다고 판단해 **최종적으로 version10은 영구 결번으로 남기고, Docling/하이브리드는 원래 번호(version11/version12)를 그대로 쓰기로 확정**했다.

### version11 — Docling(GPU) 단독 재추출
`ocr_batch_docling.py`. Docling의 레이아웃+TableFormer 모델을 GPU(CUDA)로 돌려 OCR과 표 구조를 모델이 직접 인식.
- `do_table_structure=True`, `TableFormerMode.ACCURATE`, `AcceleratorDevice.CUDA`
- 부족한 텍스트는 RapidOCR(한국어 모델, onnxruntime CUDA)로 보강
- **장점**: 테두리가 뚜렷한 표는 셀 단위로 정확히 분리(예: T21-025 3항 구성성분표)
- **한계**: 테두리 없는 표(예: T21-002 4항)는 레이아웃 모델이 "표"로 인식하지 못해 일반 본문처럼 풀어버려 `|` 구조가 사라짐 → 이 페이지는 version9보다 결과가 나쁨. 이 한계 때문에 version12를 만듦.
- GPU 적용 과정에서 `onnxruntime`(CPU)→`onnxruntime-gpu` 교체, `libcurand.so.10` 못 찾는 문제는 `LD_LIBRARY_PATH` 설정 후 프로세스 자가 재실행(`os.execv`)으로 해결.

### version12 — version9 + Docling 표 결합 (최종 보완판)
`ocr_batch_version12.py`. 본문은 version9 방식(PDF+Paddle, y좌표 행 묶기) 그대로 쓰고, **표만** Docling TableFormer 그리드로 교체:
1. version9와 동일하게 entries(텍스트+좌표) 생성
2. 텍스트층이 정상인 문서만, 같은 PDF를 Docling으로 변환해 표 그리드 감지
3. 감지된 표의 셀 텍스트가 entries와 정규화 후 70% 이상 일치하면 그 부분만 Docling 그리드로 교체
4. 매칭 실패하거나 텍스트층이 없으면 무조건 version9 그대로 둠 — version9보다 나빠지는 페이지가 없도록 설계

**실행 결과(20개 문서, 241페이지)**: Docling이 감지한 표 73개 중 68개가 매칭돼 교체됨, 5개는 매칭 실패로 version9 유지, 텍스트층 없는 4개 문서(T21-002/005/043/S003)는 version9와 100% 동일.

## 의존 관계

```
version1(이미지+OCR 별도) ──(그대로, metadata.json/combined_v2.md만 추가)──► B에게 C(전처리)로 전달
                               │
version2(OCR) ─────► run_c_preprocess.py ─► version4 + version4_analysis ─► version5(포장, 좌표 재사용)
                               │
version6_ocr(OCR) ────────────► build_c_to_b_contract.py ─► version6(포장)

version2 재실행(기본값) ─► version7

ocr_batch_version2 재사용, pipe_rows+line_numbers 고정
  └ ocr_batch_version8.py ─► version8(일부 문서) ─► version9(전체 20건, 같은 스크립트)

version3(Qwen) ──(드라이브에 "version10.zip"이라는 이름으로도 전달됨, 번호는 영구 결번 처리)

ocr_batch_docling.py(Docling GPU, 처음부터 새로 추출) ─► version11

version9 OCR 로직 + version11과 같은 Docling TableFormer(표만 선택 교체) ─► version12
```

## 번호 규칙 (앞으로 지킬 것)

1. **한 번 외부(B)에 공유한 번호는 그 의미로 영구 고정.** 다른 방법에 재사용하지 않는다 (예: version10 = version3로 고정, 영구 결번).
2. 새 방법은 항상 **지금까지 쓰인 가장 큰 번호 다음**을 쓴다. 중간에 공백(version10)이 생기더라도, 외부와 번호가 겹치는 것보다 공백이 낫다.
3. 드라이브에 폴더/zip을 올릴 때는 **코드 버전 번호를 그대로 폴더명으로 사용**한다 (`C_v0.2`, `C_v0.3` 같은 별도 라벨 체계는 쓰지 않는다).
