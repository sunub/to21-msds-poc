# 1주차 기술 명세서

- 버전: v0.2 (2026-10-25, 계획서 v0.4와 맞춤: 프롬프트 시험 3건 D-46, TO21 자료 보관 D-47, 검사 실패 시 신뢰도 D-45)
- 함께 볼 문서: 1주차 실행 계획서(노션), 결정기록(노션). 본문의 D-번호는 결정기록의 번호다.
- 이 문서는 "어떻게"를 정한다. 계획서가 누가·언제·무엇을·왜를 정한다면, 이 문서는 역할 사이에 오가는 파일의 형식, 함수의 입력과 출력, 실행 명령, 끝났는지 확인하는 방법을 정한다.

**실행 위치:** 코드는 `backend/` 아래에 있다. 이 문서의 `python scripts/...`와 `pytest` 명령은 `backend/`에서 실행한다. `data/`, `runs/`, `to21/`, `.env`는 저장소 최상위에 있고, `src/msds/common/paths.py`가 이 위치를 알고 있다.

**원칙:** 역할 사이에 오가는 것과 여러 역할이 같이 쓰는 코드는 이 저장소에 **동작하는 상태로** 들어 있다. 각 역할 안쪽의 일은 **입력·출력과 할 일이 적힌 함수 뼈대**로 들어 있고, 담당이 채운다. 공용 코드를 바꿔야 하면 혼자 고치지 말고 디스코드에 먼저 공유한다.

## 2. 공통 약속

### 2.1 문서 번호와 manifest (`data/manifest.csv`, `src/msds/common/manifest.py`)

- 문서 번호: TO21 방식. 첫 50건은 번호 그대로(25번 → `T21-025`), 추가 50건은 `T21-S003`, `T21-M001`.
- manifest는 사람이 확인한 기준표다. 스크립트가 자동으로 고치지 않는다(전처리는 다른 점만 알려 준다).

| 열 | 값 |
|---|---|
| doc_id | `T21-S016` |
| source_file | 원본 파일 이름 (확장자 포함). `data/raw/`에서 이 이름으로 찾는다. 한글 정규화(NFC/NFD) 차이는 무시한다 |
| folder | 받은 폴더 |
| purpose | 개발 / 평가 / 기타 (D-34) |
| pages | 쪽수 |
| text_layer | 정상 / 글꼴깨짐 / 없음 / 혼합 (TO21 `doc.text_layer`와 같은 값) |
| language | ko / en / mixed |
| input_mode | 이미지+글자 / 이미지만 (D-44) |
| reviewer, cross_checker | 검수 담당, 교차 확인 담당 (D-41) |
| note | 메모 |

### 2.2 경로 (`src/msds/common/paths.py`)

TO21 제공 자료는 저장소에 올리지 않고 각자 `to21/v0.6/`에 받아 둔다(D-47, 목록은 `to21/README.md`). 2026-10-29부터 작업 기준은 TO21 추출가이드 v0.6이다(v0.5와 구조가 같고 코드값만 추가. `paths.py`도 v0.6). `to21_file(kind)`는 파일이 없으면 받는 방법을 알려 주며 멈춘다.

경로는 직접 조립하지 말고 이 모듈의 함수를 쓴다. `page_png(doc_id, n)`, `page_txt(doc_id, n)`, `page_meta(doc_id)`, `silver_path(model_tag, doc_id)`, `silver_review_path(...)`, `review_sheet_path(doc_id)`, `gold_path(doc_id)`, `gold_unreviewed_path(doc_id)`, `run_dir(run_name)`, `to21_file(kind)`.

### 2.3 전처리 결과 (`data/pages/<문서번호>/meta.json`)

```json
{"doc_id": "T21-S016", "source_file": "...pdf", "page_count": 9, "dpi": 150,
 "text_layer": "정상", "language": "ko", "input_mode": "이미지+글자",
 "totals": {...}, "pages": [{"page": 1, "state": "정상", "image_cover": 0.0, "chars": 1200, ...}]}
```

쪽 상태(state): 정상 / 글꼴깨짐 / 이미지만(스캔 쪽) / 빈쪽. 텍스트층 판별 방법은 `src/msds/preprocess/render.py` 머리말에 있다.
2026-10-24에 20건으로 확인한 결과: 43번·S003만 글꼴깨짐, 나머지는 정상(S013의 11쪽은 로고만 있는 빈 쪽).

2026-10-28부터 개발용 10건의 쪽 글자는 C의 OCR 결과 2판(`data/pages/version2/`, 20건, 200dpi)을 쓴다. version2는 PDF 글자를 좌표 순서로 놓고, PDF 글자가 없는 영역과 글꼴이 깨진 쪽은 PaddleOCR로 읽은 결과다. 문서마다 `python scripts/preprocess.py --docs <문서번호> --dpi 200 --force`로 `meta.json`을 만든 뒤, `data/pages/version2/<문서번호>/`의 파일을 `data/pages/<문서번호>/`에 덮어쓴다.

| 파일 | 만든 곳 | 내용 |
|---|---|---|
| `meta.json` | preprocess.py | 위 형식 |
| `pNNN.txt` | version2 | 쪽 글자 |
| `pNNN.json` | version2 | 줄마다 글자, 좌표(bbox), 출처(`pdf_text` / `paddle`), 신뢰도, 검토 필요 여부 |
| `pNNN.png` | version2 | 200dpi 쪽 이미지 |
| `config.json`, `summary.json`, `report.md` | version2 | 처리 방식과 쪽별 통계 |

주의: `meta.json`이 있으면 `preprocess.py`는 그 문서를 건너뛴다. `--force`를 주면 version2 글자를 옛 방식 결과로 덮어쓴다.

### 2.5 모델 응답 형식 (`schema.bundle_response_schema`)

```json
{
  "doc": {"language": "ko", "msds_count": 1},                 // b1만
  "msds": [ { ...그 묶음의 키만... } ],
  "evidence": [
    {"msds_index": 0, "field": "components[0]", "page": 2,
     "source_text": "벤젠 | 71-43-2 | 99.9 이상",
     "rules": ["R04"], "note": "'99.9 이상'을 R04에 따라 하한 99.9(>=)로 나눔"}   // rules·note는 실버만
  ]
}
```

- `field`는 msds 항목 안의 경로다. 목록은 항목 단위(`components[0]`), 단일 칸은 칸 단위(`meta.last_revision_date`).
- 합치기(`common.merge.merge_bundles`)가 evidence를 TO21의 `msds[].evidence`로 옮긴다(method="vLM"). rules·note는 TO21 형식에 칸이 없어 `.review.json`으로 따로 저장한다(D-33).

### 2.6 실버 결과

- `data/silver/<모델>/<문서>.json`: TO21 스키마 그대로(작업 기준 v0.6. 10/27에 만든 실버는 v0.5 프롬프트로 뽑았고 v0.6 검증기에서 V23 버전 경고만 더 남).
- `data/silver/<모델>/<문서>.review.json`: `[{bundle, msds_index, field, page, source_text, rules, note}]`

### 2.7 칸과 경로 (`common.jsonpath`, `common.align`)

검수표·투표·성적표가 모두 같은 "칸"을 써야 결과가 맞물린다.

- **칸 하나**: 숫자 묶음(Q)·측정 조건(COND)·서술 문장(STMT)은 통째로 한 칸. 글자 목록(동의어 등)도 한 칸. 나머지는 끝 값까지 펼친다.
- **키 경로**: 목록은 순서가 아니라 "무엇인지"로 짝짓는다(TO21 채점기와 같은 기준).
  `regulations[3].applicable` → `regulations[k=7664-93-9|OSH|OSH_MEASURE|].applicable`
  성분은 CAS(없으면 이름), 규제는 성분·법령·항목, 독성은 성분·항목·지표·동물종 등. 전체 목록은 `align.LIST_KEYS`.
- 주요 함수: `keyed_flatten(msds_item)`, `unflatten_keyed(pairs)`, `item_path_map` + `to_keyed`(근거의 번호 경로 → 키 경로), `generic(path)`(번호·키를 지운 경로), `jsonpath.to_cell / from_cell`(엑셀 칸 ↔ 값).
- 한계: 키가 같은 항목이 여러 개면 나온 순서로 `#2`, `#3`을 붙인다. 이때만 순서에 따라 짝이 바뀔 수 있다.

### 2.8 우선순위 (`common.priority.priority_of`, D-32)

키 경로를 넣으면 1·2·3을 돌려준다. 물성은 필수 9종이면 1, 독성은 급성(경구·경피·흡입)이면 1, 규제는 국내 법령(OSH·KREACH·CCA·DG·WASTE)이면 1.

### 2.9 검수표 (`src/msds/review/sheet_spec.py`, D-36)

- 시트 `검수`: 열 이름과 순서는 `COLUMNS` 그대로. 검수 결과 드롭다운은 `RESULT_OPTIONS`(GPT 채택 / Claude 채택 / 수정 / 삭제 / 누락 추가).
- 시트 `문서 정보`: 문서 번호, 원본 파일, 쪽수, MSDS 순번, 검수 시작·끝 시각, 검수자, 교차 확인자.
- 경로 열은 `msds[i].` + 키 경로.
- **검수 범위(2026-10-29 기업 합의):** 1·2·3·8·9·11·12·14·15항과 머리글 관리정보(meta)만 줄을 만든다(`make_sheet.REVIEW_SECTIONS`). 항은 TO21 명세서 1_항목정의의 'MSDS 항목' 열로, 서술형은 항목 코드(S8_…), 미정의 항목은 적힌 항 번호로 정한다. 나머지 항은 골드에서 비운다(2.10).
- **줄 순서:** 항 순서(관리정보 → 1 → 2 → 3 → 8 → 9 → 11 → 12 → 14 → 15) → 문서 순서(항 안에서는 정해진 칸 → 서술 → 미정의 항목). D-36의 '우선순위 → 문제 줄 먼저' 대신이며, 우선순위·일치·원문 대조·검증기 열로 엑셀에서 걸러 볼 수 있다.
- 25번은 TO21 정답 예제를 골드로 쓰므로 검수표를 만들지 않는다.
- **검수 화면** (`backend/scripts/review_app.py --doc <문서>`): 검수표를 웹에서 고친다. 줄을 고르면 쪽 사진에 노란 상자(모델이 적은 원문 조각)·주황 테두리(값)를 칠하고, 사진 위 안내에 상자만으로 알 수 없는 사정(같은 조각이 여러 곳, 값이 조각 밖, TO21 코드·상태 구분·순번의 풀이)을 적는다. 위치는 PDF 글자층에서, 글자층이 깨진 쪽은 C의 OCR 결과(`data/pages/<문서>/p00N.ocr.json`, `scripts/ocr_pages.py`)에서 찾는다. OCR 결과가 없는 쪽은 상자 없이 연다.
  - **문장 카드와 색 칩** (`scripts/review_cards.py`): 목록 항목 하나를 문장 하나로 보이고, 판단할 칸은 색 칩(왼쪽 사진의 같은 색 밑줄)이다. 칩을 누르면 짧은 풀이(용어·코드 이름·상태 뜻)가 나온다. 칩이 회색 점선이면 쪽에서 근거를 못 찾은 칸이라 원문에서 직접 찾는다. 문서마다 다른 규칙은 두지 않는다.
  - **카드 판단:** '✓ 같아요'(모델 채택), '✗ 다른 칩이 있어요'(칩을 눌러 고침), '원문에 없어요'(카드 전체 삭제. 이미 확인한 칸도 함께 삭제해 반쪽 항목을 남기지 않고, 고친 값·근거 줄·쪽은 비우며, 메모가 있으면 그대로 둔다. 사람이 넣은 누락 추가 줄은 '삭제' 대신 줄을 지운다), '되돌리기'(방금 한 카드 판단만. 화면이 판단 전 줄을 간직했다가 `/api/restore`로 사람 열을 원래 셀 값 그대로(숫자는 숫자, 엑셀이 바꾼 날짜는 날짜, 앞뒤 공백도) 다시 쓰고, 지운 누락 추가 줄은 '빠진 칸 추가'와 같은 경로·스키마·검수 범위 검사를 거쳐 다시 넣는다. 수식으로 적힌 칸(`=…`)만 실행되지 않게 글자로 되돌린다. 판단 뒤 그 카드의 줄을 다른 길(자세히·메모 등)로 고치면 되돌리기 단추는 사라진다. 처리하는 동안 그 카드 단추는 잠긴다. 그 쪽을 떠나면 되돌릴 수 없다). 직접 넣은 줄만 있는 카드는 '원문에 없어요'로 줄을 한 번에 지우고(하나라도 못 지우면 하나도 안 지움), 카드가 없어지므로 위쪽 막대의 '방금 지운 카드 되돌리기'로 다시 넣는다(이 쪽을 보는 동안만). 칸의 지금 값은 골드와 같은 규칙이다: '수정'·'누락 추가' 줄만 수정값, 나머지는 AI 값(엑셀에 남은 수정값은 보지 않는다). 고치기 양식의 처음 값·근거 줄·쪽도 같은 규칙이다. 검수 결과는 앞뒤 공백을 떼고 본다(교차 확인 반영의 미검수 세기도). 엑셀에서만 생기는 '수정인데 수정값이 빔'(골드 빈칸)·'값이 없는 쪽을 채택'(골드에서 항목 삭제)은 확인한 칸으로 세지 않는다: 칩에 ⚠(골드에서 어떻게 되는지와 '다른 칩이 있어요'로 고치라는 안내), 카드는 '✔ 확인했어요' 대신 '⚠ N칸 다시 골라 주세요'. '같아요'는 이런 칸을 바꾸지 않는다. 칸별로 보려면 '자세히(칸별)'.
  - **화면 갱신·저장:** 줄을 바꾸는 모든 길(저장·묶음 저장·누락 추가·줄 지우기·되돌리기·교차 확인 반영)은 서버가 같은 꼴(`_update`: 바뀐 줄, 없어진 줄, 카드·풀이·칸 정보)로 답하고 화면은 한 함수(`apply`)로 반영한다. 다른 카드에 영향을 주는 변화(골드에서 빠지는 항목이 달라짐, 성분표·순번 줄의 지금 값이 바뀌거나 줄이 생기고 없어짐)면 문서의 모든 카드를 다시 받고(T21-043 약 0.8초), 아니면 그 카드만(값이 그대로인 '같아요'는 성분표 카드여도 그 카드만). 교차 확인 반영은 남은 칸 자리·되돌리기를 건드리지 않는다. 줄 저장·넣기·전부 맞음 단추는 처리하는 동안 잠기고, 그동안 누른 저장(Ctrl+Enter 포함)은 '저장하는 중이에요'로 알린다. 저장 뒤 다시 그려도 다른 카드에 열어 둔 양식은 닫지 않고, 적던 글·커서·'저장될 값' 글을 그대로 두며, 치던 칸은 포커스를 준 뒤 화면 위치를 맞춰 제자리에 둔다. 미리보기의 형식 오류는 칸 모양별 쉬운 말(목록에서 고르기 / 숫자만 / 형식이 맞지 않아요(명세서 보기 값) / 이 칸에 맞지 않는 값)로, 나눠 적는 칸이면 어느 칸인지 붙여(예: '온도 단위: 목록에서 골라 주세요') 알린다. 대상 성분·상위 성분 번호를 고쳐 저장할 때는 같은 MSDS 건 성분표의 순번(골드에 남는 성분)이나 MIX인지 서버가 확인한다. 바뀐 것이 없는 고치기는 맞음과 같은 길이라 막지 않고, 맞음·같아요로 둔 대상 성분이 골드에서 빠지는 성분을 가리키면 칩에 ⚠('가리키는 성분이 골드에서 빠져요'). 이름 칸(교차 확인자 등)도 수식이 되지 않게 글자로 쓴다. 저장하지 못하면 까닭(엑셀 잠금 파일 / 쓰기 권한 없음 / 그 밖)을 알린다.
  - **골드에서 빠지는 항목:** 골드는 목록 항목 안 줄 하나라도 '삭제'(값이 없는 모델 채택 포함)면 그 항목 전체를(하위 항목까지) 빼고, 항목 자체인 한 칸(문장 등)을 비워도 그 항목을 뺀다(`build_gold._assemble`, 팀 규칙). 화면은 같은 판단(`review_cards.dropped`: 골드의 `_decide`·`_items`를 그대로 쓰고, 기본값 모델도 골드와 같은 함수 `build_gold.default_model`(build_gold_file도 이것을 쓴다))으로 그 카드와 하위 항목 카드에 '이 항목은 골드에서 빠져요'와 까닭(어느 칸, 상위 항목이면 그렇다고)을 보이고, 판단 단추 대신 '삭제한 칸 되돌리기'(그 칸을 미검수로: 판단·고친 값·검수자를 비우고 메모는 남김)와, 상위 항목 때문이면 '상위 항목 카드로 가기'(상위 카드가 지금 쪽에도 있으면 쪽을 옮기지 않음)를 준다. 그런 카드의 미판단 줄은 볼 필요가 없어 진행률·남은 칸·남은 필수 칸에서 뺀다(저장은 안 함). 순번 형제·성분명 표·대상 성분 고르기에서도 뺀다. 칩 고치기의 삭제와 칸별 '삭제'는 이 사실과 함께 빠질 하위 항목 카드 수(목록 항목일 때만. 목록 항목이 아닌 카드는 칸만 지워지고 아래 카드는 남는다)를 알리고(확인 창, 카드 '원문에 없어요'도), 칸 모양별 '비움으로 저장'을 준다: null을 받는 칸은 null, 배열 칸(관용명·표기 등)은 빈 목록 [], 글 칸은 빈 글 — 그 칸만 비고 항목은 남는다. 비울 수 없는 칸이면 비움을 권하지 않고 맞는 값을 적으라고 한다. 항목 전체가 원문에 없으면 카드의 '원문에 없어요'.
  - **화면이 확인하는 숨긴 칸:** 순번·쪽·항 번호, 코드에서 정해지는 칸(P 문구 종류 등), 수치와 같은 상태는 화면이 확인해 '화면이 확인함 ✓'에 둔다. 순번은 목록 순서(실버 항목은 실버에 적힌 순서. 엑셀에서 줄을 정렬해도 같다. 사람이 넣은 항목은 그 지금 순번 값 자리)대로, 형제들의 지금 값(고친 순번, 사람이 넣은 항목의 순번. 골드에서 빠지는 항목은 빼고)으로 1, 2, 3…이어야 하고(건너뛴 번호는 그 줄 모델의 실버에서 그 번호가 검수 범위 밖 항의 항목일 때만 허용, 아니면 '순번 3이 빠졌어요'. 실버가 바뀌면 다시 읽는다), 항목마다 1부터 다시 세는 것은 물리화학적 특성(physchem)만 허용한다. 확인이 안 되면 칩으로 꺼내 보인다.
  - **코드 ⚠:** 원문 표기가 같은 갈래의 더 긴 다른 코드 표기 안에만 있을 때만 칩에 ⚠를 붙인다('특별관리대상물질' 속 '관리대상물질').
  - **바꾼 것이 없는 고치기**(값·근거 줄·쪽이 모델과 같음)는 '수정'이 아니라 맞음(모델 채택)으로 저장한다.
  - **처음 사용법·필수 칸:** 첫 화면에 실제 화면을 짚는 사용법이 뜨고('? 사용법'으로 다시 봄), 위쪽 막대에 진행률과 남은 필수 칸 수가 나온다.
  - **JSON을 몰라도 고치는 입력:** 칸 모양(TO21 스키마)에 맞는 입력칸을 준다. 정해진 값·예/아니오·대상 성분은 이름으로 고르고, 수치(Q)는 원문 표기('> 2000 mg/kg')만 적으면 R04대로 나눈다(`extract.rows.parse_qm`·`extract.expand.fill_q`). 문장은 소제목·내용, 측정 조건은 칸을 나눠 적는다. 저장 전에 '저장될 값'을 보여 주고, 스키마에 맞지 않으면 저장하지 않고 이유를 알린다.
  - **빠진 칸·항목 추가:** 카드의 '빠진 칸·항목 추가'에서 네 가지 중 하나를 고른다: 이 카드에 빠진 칸, 같은 종류 새 줄(★ 항목을 가르는 칸을 채움), 하위 목록의 새 항목(연락처 등), 표에 맞는 자리가 없는 내용(미정의 항목). 경로(`[k=…]`)는 화면이 `align.LIST_KEYS`로 만든다. 순번 칸에는 '순번은 원문 목록에서의 차례'라는 안내를 붙인다(화면은 같은 목록의 순번끼리만 확인하고 원문 위치는 확인하지 못한다). 원문 조각은 쪽 사진에서 줄을 눌러 채운다. 같은 목록에 같은 내용이 이미 있으면 저장 전에 묻는다(이미 삭제한 항목은 세지 않고, 미정의 항목은 순번·사유를 빼고 견준다).
  - **파란 점선:** 검수 범위 안인데 어떤 칸의 근거로도 쓰이지 않은 원문 줄(머리말·꼬리말·항 제목 제외). 모델이 통째로 빠뜨린 값을 찾는 데 쓴다.
  - **필수 칸만:** TO21 채점기가 필수 항목으로 비교하는 칸만 보인다(작은 골드: 개발용 2~3건 필수 항목 검수).
  - **같은 원문 줄이 두 표에 들어간 카드:** 같은 MSDS·같은 쪽에서 공백 뺀 근거 줄이 같고 그 쪽 글자층에 한 번만 나오면(6글자 이상) 겹침으로 본다(`review_cards.OVERLAP_RULES`, 문서 무관). TO21 기준으로 맞는 표가 정해진 쌍(규제 DG↔위험물, 규제 WASTE↔폐기물, 발암·변이·생식 독성↔cmr, 생태↔서술, 국제분류↔규제 INTL, 독성↔서술, extras↔정식 표)은 맞지 않는 카드에 ⚠ 띠와 '그 카드로 가기', 맞는 카드에 작은 안내를 보이고, 규칙 없는 쌍은 안내만 한다. 한쪽이 삭제되면 띠가 사라진다.
  - 값 없는 행에 표기 규칙(`common.conventions`)으로 채운 지표·기준 종류는 '표기 규칙으로 넣는 값'이라고 풀이한다.
- **두 모델이 모두 비워 둔 칸은 행을 만들지 않는다.** 두 모델이 함께 빠뜨린 항목은 개수 세기로 찾아 "누락 추가" 줄을 직접 넣는다.
- 수정값(엑셀에서 직접 적을 때): 객체·목록은 한 줄 JSON으로 적는다. 검수 화면은 칸 모양대로 바꿔 적는다. 숫자처럼 보이는 글자를 글자로 남기려면 따옴표로 감싼다(`"01"`).
- 검수 결과를 비워 둔 칸은 미검수다. 골드에는 `DEFAULT_MODEL`의 값이 들어가고 `.unreviewed.json`에 기록되며 성적표에서 "참고"로 표시된다(D-35). `DEFAULT_MODEL`은 프롬프트를 고정한 뒤 25번 실버를 TO21 정답 예제로 채점해 점수가 높은 모델로 A가 정한다.

## 3. 모델 호출 (`src/msds/extract/client.py`, D-44)

- 교육원 키는 **MonoRouter**(`https://monogpt.kr/api/monorouter/v1`), RunPod은 **vLLM**. 둘 다 OpenAI 호환 **Chat Completions**다. 같은 코드로 부르고 `configs/models.yaml`의 모델 이름만 바꾼다.
- 입력: 쪽마다 `=== 쪽 N ===` + 텍스트층(이미지+글자 모드이고 그 쪽이 정상일 때) + 쪽 이미지(base64 PNG).
- 구조화 출력은 `structured` 순서대로 시도한다.
  - `json_schema`가 거부(400 등)되면 `json_object`, 그다음 `none`으로 넘어간다. 받아들여진 방식은 기억해 다음 호출부터 바로 쓴다.
  - 응답은 묶음 응답 스키마로 검증하고, 실패하면 오류 목록을 붙여 `max_retries`번 다시 요청한다.
  - 그래도 실패하면 읽을 수 있는 JSON은 넘겨서 쓸 수 있는 부분은 쓰고, 오류는 기록에 남긴다.
- 출력 길이 한도에 걸리면(`finish_reason=length`) 그 묶음은 실패로 기록한다. 대응은 묶음을 더 쪼개거나 `max_tokens`를 늘리는 것이다(계획서 14장).
- 대체 모델: 실패하면 `fallback_models` 순서로 한 번 더 시도한다(Claude: fable-5 → opus-5, 기준선: Qwen3.8 → Qwen3.6).
- 출력 한도 이름: GPT-5 계열은 `max_completion_tokens`(`token_param`으로 설정). 400 오류에 max_tokens가 언급되면 자동으로 바꾼다.

시작점(모델 카드의 vLLM 레시피를 우선한다):

```bash
vllm serve Qwen/Qwen3.8-27B --max-model-len 131072 --limit-mm-per-prompt '{"image": 40}' --gpu-memory-utilization 0.92
```

- 문서 한 건을 통째로 넣으므로 입력이 길다(150dpi 기준 쪽당 대략 수천 토큰, 17쪽 문서는 수만 토큰). `--max-model-len`과 쪽 이미지 수 한도(`--limit-mm-per-prompt`)를 문서 쪽수에 맞춘다. 39번(37쪽)은 2주차 평가용이라 1주차에는 해당 없다.
- 생각 모드는 `configs/models.yaml`의 `chat_template_kwargs: {enable_thinking: false}`로 끈다. 이 모델에서 이 이름이 맞는지 모델 카드로 확인한다.
- 서버 주소는 `.env`의 `VLLM_BASE_URL`(예: `http://<pod 주소>:8000/v1`).

## 4. 프롬프트 (`src/msds/extract/prompts/`, `prompt_builder.py`)

**구성**: 한 번 호출할 때 아래를 이어 붙인다.
1. `system.md`: 역할, 입력 설명, 모든 칸에 적용하는 원칙(보이는 것만, 없으면 null, 원문 그대로, 목록 빠짐없이 등)
2. `output_silver.md` 또는 `output_baseline.md`: 근거(evidence) 작성법. 실버만 규칙 번호·설명을 추가로 요구한다(D-37)
3. `b1.md`~`b5.md`: 이번 묶음 안내 + TO21 명세서에서 꺼낸 [필드 정의] [규칙] [공통 구조] [코드표] [동의어]
4. (b2~b5) `[성분 목록]`: b1 결과로 만든 성분 번호 목록
5. 문서 전체 쪽

**만드는 법**: `b1.md`~`b5.md`는 `python scripts/build_prompts.py`로 TO21 명세서에서 만든다. 직접 고치지 말고 `prompt_builder.py`의 `GUIDES`(묶음 안내)나 규칙 목록을 고친 뒤 다시 만든다. TO21이 명세서를 고치면 다시 만들기만 하면 된다.

**원칙 (D-43, D-46)**
- 프롬프트는 개발용 3건으로 시험한 뒤 고정한다: S016(단일물질, 독성 정보 많음), M013(혼합물, 성분 8개·함유량 범위·쪽을 넘는 성분 표), S003(텍스트층 깨짐, 쪽 이미지만 입력). 평가용 문서(25번 포함)는 프롬프트를 고정한 뒤에만 돌리고, 그 결과를 보고 프롬프트를 고치지 않는다. 스크립트가 `--allow-eval` 없이는 평가용 문서를 돌리지 않는다.
- 평가용 문서의 내용을 예시로 넣지 않는다. 1주차 프롬프트는 예시 문서 없이 규칙만 쓴다.
- 참고: TO21 명세서의 "예시(가상)" 값 일부(황산, 7664-93-9 등)가 25번 문서와 겹친다. 명세서 원문이라 그대로 두었고, 25번 점수를 해석할 때 이 점을 함께 적는다.
- 프롬프트를 고치면 `PROMPT_VERSION`(p1 → p2 …)을 올린다. 실행 기록에 버전이 남는다.

**2주차 변형 프롬프트 (D-40)**: 규칙은 그대로 두고 읽는 순서와 방법만 바꾼다(예: 표를 먼저 행 단위로 옮겨 적은 뒤 채우기). `output_*.md`처럼 파일을 하나 더 두고 runner에 선택 인자를 추가하는 방식으로 넣는다.

## 6. 검수하는 법 (검수 전원)

계획서 13장(검수 가이드)이 기준이다. 검수 화면에서는 카드를 눌러 왼쪽 노란 줄과 문장을 견주고, 같으면 '✓ 같아요', 틀린 칩이 있으면 '✗ 다른 칩이 있어요', 원문에 없으면 '원문에 없어요'를 누른다(2.9). 엑셀에서는 아래만 기억한다.
- `우선순위` 1부터, `일치`가 불일치·한쪽만인 줄부터, `원문 대조`가 불일치인 줄부터 본다.
- `검수 결과`를 고른다. 수정이면 `수정값`·`수정 원문 조각`·`수정 쪽`을 적는다.
- 두 모델이 함께 빠뜨린 항목은 검수 화면의 '빠진 칸·항목 추가'로 넣는다(경로를 쓰지 않는다). 엑셀에서 넣을 때는 맨 아래에 새 줄을 넣고 `검수 결과`를 "누락 추가"로, 경로는 같은 종류의 다른 줄을 참고해 적는다.
- `문서 정보` 시트에 검수 시작·끝 시각을 적는다.
- 판단이 어려우면 `메모`에 적고 디스코드에 공유한다. 혼자 정하지 않는다.
