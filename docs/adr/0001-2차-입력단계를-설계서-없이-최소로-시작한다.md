# 2차 입력 단계(로더·판별기·지식 함수 형태)를 설계서 없이 최소 범위로 시작한다

역할 D 가이드는 입력 칸 목록, 판정 용어, 지식 함수의 메시지 명세, 단일/혼합 판별 기준을 "TO21 정합성검증 개발설계서 v0.2"에서 가져오라고 하지만, 이 문서는 `to21/v0.5/`에도 `msds-bench/`에도 없다(2026-10-26 확인). 그래서 25번 황산 예제와 가이드 예시 코드로 확인되는 범위까지만 구현하고, 설계서가 있어야 정할 수 있는 것은 정하지 않고 비워 둔다. 설계서를 받으면 아래 "보류한 것"부터 채운다.

## 정한 것

- **기준 데이터는 25번 황산(TO21 정답 예제) 한 건이다.** 골드 10건은 형태가 확정되지 않았고 10/26 21:00 이후에야 나온다. 골드의 구조는 TO21 스키마 v0.5가 정하므로 예제와 같은 형식으로 읽는다.
- **판별기는 표기를 우선하고, 폴백은 성분 개수만 쓴다.**
  - `composition.type`이 `단일물질`/`혼합물`이면 그대로 따른다(황산은 `혼합물`).
  - 표기가 없고 성분이 2개 이상이면 `혼합물`로 추정하고, `basis`에 "표기 없음, 성분 개수로 추정"이라고 남긴다.
  - 표기가 없고 성분이 1개 이하이면 `판단불가`로 둔다.
- **시험은 25번 시험과 파일이 필요 없는 인라인 최소 케이스 2~3개로 쓴다.** 25번 JSON은 git에 올라가지 않아(D-47) 파일이 없으면 25번 시험이 전부 skip 되기 때문이다.
- **`d_check.py`는 기본 동작만 미리 만든다.** 입력은 경로 인자로 받고, 출력에 "미검수 구분 없음 (참고용)"을 고정 문구로 넣는다.
- **검증기 규칙(V01~V23)과 `comp_map` 로직은 다시 시험하지 않는다.** 이미 `to21/v0.5/` 검증기와 `backend/tests/test_common.py`가 책임진다.

## 보류한 것과 이유

| 보류 | 이유 | 설계서를 받으면 |
|---|---|---|
| 가이드 예시의 "성분 1개 + 함유량 하한 80% 이상이면 단일물질" 폴백 | 가이드가 "예시 기준"이라고 쓰고, 근거 없는 기준은 `판단불가`로 두라고 한다(6장). 근거를 확인할 수 없는 임계값은 조용히 오판정을 만든다 | 기준이 있으면 폴백에 추가하고 출처를 주석에 적는다 |
| 물처럼 유해성 없는 성분만 섞인 수용액의 처리 | 가이드가 설계서에서 찾으라고 하고, 없으면 멘토링 질문으로 F에게 넘기라고 한다. 황산(황산 93~98% + 물 2~7%)이 바로 이 사례다 | 설계서에 규정이 있으면 반영하고, 없으면 멘토링 질문으로 확정한다 |
| `missing`에 넣을 칸의 확정 목록 | "없으면 판정할 수 없는 값"의 기준이 설계서에 있다. 지금은 가이드 예시의 최소 목록(기준일, `composition.type`, 성분, `hazard.classes`, `hazard.signal_word`)만 둔다 | 설계서 기준으로 더하거나 뺀다 |
| 9항 `physchem`을 설계서가 쓰는 특성만 남기는 필터 | 어떤 `prop_code`를 쓰는지가 설계서에 있다. 지금은 모든 행을 넘긴다 | `prop_code`로 거른다. 동점도 코드는 TO21 명세서 코드표에서 확인한다 |
| 지식 함수 3개의 확정된 반환 형태 | 설계서의 메시지 명세가 기준이다. 지금은 가이드 예시를 "임시"라고 docstring에 명시해 둔다 | 명세에 맞춰 docstring을 고친다 |
| 판정 용어와 심각도(일치/불일치/경계/근거부족)의 코드 반영 | 이번 범위에는 판정 단계가 없다. `msds-bench/`의 "통과/경고/위반"은 용어가 달라 대체할 수 없다 | 3단계(단일물질 2항)를 만들 때 설계서 용어를 쓴다 |
| 혼합물 계산(함량 하한·상한 두 번 계산, 한계농도, 가산 규칙) | 설계서에만 있는 방법이고 1주차 범위(1~2단계의 형태)가 아니다 | 5단계에서 구현한다 |
| 미검수 칸 구분을 `d_check.py` 보고에 반영 | 미검수 목록의 위치와 형식이 문서에 정해져 있지 않다. `paths.gold_unreviewed_path`는 F 가이드에만 나오고 저장소에 없다 | A에게 형식을 확인한 뒤 몇 줄 더한다 |

## 다른 방안과 비교

- **설계서가 올 때까지 모두 보류한다:** 로더와 판별기는 25번 예제만으로 만들고 검증할 수 있고, 10/27 보고에 "1단계가 골드에서 동작하는가"가 들어가므로 일정에 맞지 않는다.
- **가이드 예시를 그대로 따른다(80% 포함):** 근거 없는 임계값이 코드에 굳고, 설계서와 다르면 판정이 틀린 채 남는다.
- **`msds-bench/`의 문서를 설계서 대신 쓴다:** 그 폴더에는 판정 용어, 입력 칸, 지식 함수, 혼합물 계산이 모두 없다. 1차 추출 검증 도구와 법령 목록이 있을 뿐이다.

## 결과

- 지식 함수 형태와 `missing` 목록은 설계서 확인 시 바뀔 수 있다. 호출하는 쪽(3단계 이후)이 생기기 전에 바꾸면 비용이 작다.
- 판별 결과가 `판단불가`인 문서는 사람에게 넘기는 것이 맞다. 설계서의 원칙("애매하면 사람")과 같은 방향이다.
- `get_regulation` 반환 칸은 E 가이드 3.4의 15항 규칙표 칸 구성(`law, item_code, item_name, cas_no, threshold_op, threshold_value, threshold_unit, valid_from, source, note`)을 기준으로 한다. D 가이드는 "E의 머리글에 D가 맞춘다", E 가이드는 "D의 `get_regulation` 칸 이름에 E가 맞춘다"고 서로 반대로 적어 어느 쪽도 정하지 못하는 상태였다. 실제 칸 목록이 E 가이드에 이미 있으므로 그것을 따라 순환을 끊고, E에게는 확인만 요청한다. `cas_no`는 조회 키라 반환 행에 담을지, `note`를 넘길지는 구현 때 docstring에 남긴다.
