# A1 작업 흐름 실행과 검증

기존 `msds.api.extract_app`에 PostgreSQL 대기열을 연결한다. 업로드한 PDF와 작업 시도별 산출물은 공유 파일 저장소에, 작업 상태·임대·진행 정보는 `extract.jobs`에 저장한다. 전처리와 추출은 별도 대기열이며 기존 결과·검수 API 경로를 유지한다. 설정하지 않으면 기존 파일 기반 단일 작업자가 동작한다.

## 준비

- 프로젝트, Python 의존성, TO21 명세와 모델 설정을 준비한다. 원본 파일과 모델 출력은 Git에 넣지 않는다.
- PostgreSQL 접속 계정에 `extract.jobs`의 SELECT·INSERT·UPDATE 권한을 부여한다. 테스트에는 기존 데이터를 사용하지 않는 별도 DB를 권장한다.
- 대상 DB에 `extract.jobs`가 없는 신규 환경에서만 `backend/migrations/a1_0001_extract_jobs.sql`을 적용한다. 이 SQL은 기존 테이블을 변경하거나 삭제하지 않고, 이미 존재하면 실패한다. 적용 전에 `extract` 스키마를 준비하고, 기존 테이블이 있으면 정의와 마이그레이션 이력을 먼저 확인한다.
- DB 모드로 시작할 때 필수 컬럼을 검사한다. 테이블이 없거나 구버전 정의인 경우 서버 시작이 실패하며, 기존 테이블을 자동으로 변경하지 않는다.
- 여러 API/작업자 프로세스는 같은 DB와 같은 `data/service` 파일 경로를 사용해야 한다. 각 컨테이너의 로컬 디스크가 서로 다르면 안 된다.

예를 들어 개발용 PostgreSQL 컨테이너에 접속 상태와 테이블을 확인한다. `.env` 경로와 호스트 포트는 각 환경에 맞춘다.

```bash
docker compose --env-file deploy/htodb/.env -f deploy/htodb/compose.yaml exec pg \
  psql -U kdb -d kdb -c '\dt extract.jobs'
```

## 실행

추출과 판정, 화면은 한 앱으로 8020에 띄운다. 판정 API를 8011에 따로 띄우던 방식은 추출 앱에 라우터가 붙기 전의 임시 방법이다. 화면은 8020만 부른다.

```bash
backend/scripts/serve_api.sh
```

`deploy/htodb/.env`의 접속 정보로 `msds_service` DB를 쓴다. 처음 한 번 `apply_erd_migrations.py`와 `b2_migrate.py --database msds_service`로 DB를 준비한다. `kdb`에 `b2_migrate.py --dev`를 돌리면 대역 표 때문에 실제 `a2_0003` 마이그레이션이 실패하므로, 서비스 DB에는 `--dev`를 쓰지 않는다. 지식DB 조회 API(8010)는 판정에 필요하지 않으며 사람이 직접 조회할 때만 띄운다.

아래는 환경 변수를 직접 지정하는 방법이다. `MSDS_SERVICE_DATABASE_URL`은 libpq 접속 문자열이다. 아래는 로컬 개발 예시다. 비밀번호를 셸 명령 기록에 넣지 않도록 입력 프롬프트로 받는다. 다른 운영 환경에서는 팀의 비밀 관리 방식을 따른다.

```bash
cd ~/to21-msds-poc/backend
export MSDS_SERVICE_DATABASE_URL='host=127.0.0.1 port=5434 dbname=kdb user=kdb'
read -rs -p 'PostgreSQL 비밀번호: ' PGPASSWORD
echo
export PGPASSWORD
export MSDS_PREPROCESS_WORKERS=1
export MSDS_EXTRACT_WORKERS=1
export MSDS_MODEL_MAX_INFLIGHT=16
.venv/bin/uvicorn --app-dir src msds.api.extract_app:app --port 8020
```

B2 판정 테이블을 같은 DB에 설치한 뒤 한 앱에서 판정 API도 제공하려면 `JUDGE_PG_PASSWORD`가 설정된 상태에서 `MSDS_JUDGE_IN_EXTRACT_APP=1`을 추가한다. 이때 `/api/judgments` 라우터와 판정 작업자가 추출 앱의 시작·종료에 함께 연결된다. B2를 별도 서버로 실행하거나 판정 DB가 준비되지 않았다면 이 변수를 설정하지 않는다.

환경 변수는 프로세스별 설정이다. 여러 프로세스를 띄우면 전처리·추출 작업자 수가 프로세스마다 늘어난다. `MSDS_MODEL_MAX_INFLIGHT` 기본값은 16이고 같은 게이트를 쓰는 프로세스는 같은 값을 사용해야 한다. 기본값은 기존 호출 상한일 뿐 동시 추출 실험으로 검증된 운영값은 아니다.

공용 모델 게이트는 기본적으로 `/tmp/to21-msds-model-gate-<UID>`를 사용한다. `MSDS_MODEL_GATE_DIR`로 경로를 바꿀 수 있으며 같은 호스트에서 같은 사용자와 **같은 로컬 파일시스템 경로**를 공유해야 전체 제한이 적용된다. 네트워크 파일시스템이나 여러 호스트에 걸친 제한은 지원하지 않는다. 게이트 디렉터리는 사용자만 접근할 수 있어야 한다.

## 동작

- 작업 등록은 DB 대기열에 기록되고, 전처리와 추출 작업자가 `FOR UPDATE SKIP LOCKED`로 서로 다른 작업을 가져간다.
- 임대 갱신이 끊긴 작업은 재대기한다. 각 실행은 다른 산출물 폴더에 쓰고 유효한 임대 소유자만 결과를 게시하므로 이전 작업자가 늦게 끝나도 새 결과를 덮지 않는다. 기존 결과의 보존 및 파일 저장소 백업은 별도로 관리한다.
- 작업 실패는 자동으로 한 번 더 시도하고, 다시 실패하면 `failed`로 남긴다. `/api/documents/{id}/retry`로 수동 재시도할 수 있다.
- 목록·상세의 `queue_position`은 해당 단계 대기열에서 1부터 계산한다. `eta_seconds`는 최근 정상 완료된 작업 3건 이상의 실행 시간과 대기·실행 작업 수를 이용한 대략적인 완료 예상 시간이다. 표본이 부족하면 `null`이다. 두 단계의 대기와 각 단계의 다른 작업자 수, 현재 실행의 남은 시간을 정확하게 반영한 보장은 아니다.
- 기존 파일 기반으로 처리했던 작업을 DB로 자동 이관하지 않는다. DB 모드에서는 새로 등록한 작업을 DB에서 조회한다.
- 현재 작업자는 기존 `pipeline.Steps`의 전처리·분할·추출 함수를 사용한다. A2의 `process(job_id, ctx)` 계약과 `checks_done`·`handoff` 이벤트는 아직 연결하지 않았으므로, 현재 `done`은 기존 추출 파이프라인이 끝났다는 뜻이며 판정용 넘김 기록이 생성됐다는 뜻이 아니다.
- DB 등록 결과가 불확실하면 원본 PDF를 삭제하지 않아 DB 행이 없는 파일이 남을 수 있다. 이 경우 운영자가 DB와 파일을 대조한 후 정리한다. DB 상태와 파일 저장소를 함께 백업해야 한다.

## 검증과 실험

일반 회귀 시험은 `cd backend && .venv/bin/python -m pytest -q tests/test_E_service.py tests/test_E_extract_app.py tests/test_model_gate.py tests/test_a1_worker.py tests/test_a1_jobs_api.py tests/test_a1_preprocess_isolation.py`로 실행한다. PostgreSQL 시험은 **별도 임시 DB**의 접속 문자열을 `MSDS_TEST_DATABASE_URL`에 지정한 뒤 `tests/test_a1_jobs_postgres.py`를 실행한다. 시험은 임시 스키마를 생성·삭제하므로 실제 서비스 DB를 지정하지 않는다.

실제 모델과 문서를 사용하는 동시 추출 실험 방법과 아직 측정하지 않은 사항은 [동시 추출 실험 ADR](adr/0006-a1-동시-추출-실험.md)을 따른다. 실측 전에는 운영 N이나 일관성 목표 달성을 확정하지 않는다.
