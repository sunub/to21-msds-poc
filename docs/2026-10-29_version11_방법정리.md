# version11 방법 정리

Docling(GPU)의 레이아웃 + TableFormer 모델로 OCR/표 구조를 처음부터 끝까지 전부 다시 뽑은 버전.

## 코드

- 파일: `backend/scripts/ocr_batch_docling.py`
- 사용법:
  ```
  uv run python3 backend/scripts/ocr_batch_docling.py --doc-id T21-025 --output-version version11
  uv run python3 backend/scripts/ocr_batch_docling.py --output-version version11   # 전체 20건
  ```

## 핵심 방법

- version2/9처럼 "PDF 텍스트 + PaddleOCR를 우리가 직접 좌표로 합치는" 방식이 아니라, **Docling이라는 문서 파싱 라이브러리에 PDF를 통째로 맡겨서** 레이아웃 인식부터 표 구조 인식까지 전부 모델이 처리하도록 함.
- `PdfPipelineOptions`:
  - `do_table_structure = True`, `table_structure_options.mode = TableFormerMode.ACCURATE` — TableFormer 모델이 표의 행/열/셀 경계를 직접 인식.
  - `accelerator_options = AcceleratorOptions(device=AcceleratorDevice.CUDA)` — 레이아웃/TableFormer 모델을 GPU로 실행.
  - `images_scale = 200/72` — 다른 버전들과 동일한 200DPI 기준.
- 텍스트가 부족한(이미지뿐인) 페이지는 Docling 내부의 OCR 보조 엔진인 **RapidOCR**이 텍스트를 보강. `RapidOcrOptions(lang=["korean"], backend="onnxruntime", ...)`로 한국어 인식 모델을 지정.
- 페이지 출력(`page_text()`)은 Docling이 추출한 문서 구조를 순서대로 돌면서(`doc.iterate_items()`), `TableItem`은 그 그리드를 `|`로 join해서 여러 행으로, 그 외 텍스트는 그대로 한 줄씩 써서 만듦. `line_numbers=True`면 전체에 `L001...` 매김.

## GPU(CUDA) 적용 관련 이슈와 해결

1. **RapidOCR 한국어 모델은 onnxruntime 백엔드에만 있음** — torch 백엔드로 바꿔도 `korean.mobile` 조합이 없어서 실패. → onnxruntime 백엔드 유지, `RapidOcrOptions.rapidocr_params`에 `EngineConfig.onnxruntime.use_cuda: True`를 넘겨 CUDAExecutionProvider를 쓰도록 강제.
2. **onnxruntime(CPU 전용) → onnxruntime-gpu 교체** 필요 (`uv add onnxruntime-gpu`, 기존 `onnxruntime` 제거).
3. **`libcurand.so.10` 못 찾음 에러** — onnxruntime-gpu가 필요로 하는 CUDA 런타임 라이브러리가 시스템 경로엔 없고 torch가 설치한 `nvidia-curand` 등 pip 패키지 안에만 있었음. `os.environ["LD_LIBRARY_PATH"]`를 런타임에 바꿔도 이미 시작된 프로세스의 동적 링커에는 반영이 안 되기 때문에, **스크립트가 시작할 때 `LD_LIBRARY_PATH`를 nvidia pip 패키지들의 `lib` 디렉터리로 설정하고 `os.execv`로 자기 자신을 한 번 재실행**하도록 처리(`_exec_with_nvidia_pip_libs_on_ld_path()`).
4. 위 조치 후 `onnxruntime.get_available_providers()`에 `CUDAExecutionProvider`가 포함되고, "CPU로 자동 전환" 경고가 사라짐을 직접 확인.

## 파일 구조

다른 버전들과 동일하게 `data/pages/version11/{doc_id}/pNNN.png` + `pNNN.txt` 쌍으로 저장. `pNNN.png`는 새로 렌더링하지 않고 `data/pages/{doc_id}`(없으면 `version1`)의 기존 200DPI 렌더를 그대로 복사.

## 결과 (20개 문서, 241페이지 전체 실행)

- 전체 처리 시간: 약 65초 (GPU 적용, 문서당 1~7초)
- 텍스트층이 정상인 문서는 표가 상당히 정확하게 셀 단위로 분리됨 (예: T21-025 3항 구성성분표 `화학물질명 | 관용명 및 이명 | CAS 번호 또는 식별번호 | 함유량(%)`)

## ⚠️ 페이지별 시간(`summary.json`)은 의미 없는 값이다

`data/pages/version11/{doc_id}/summary.json`에 페이지별 `seconds` 항목이 있지만, 전부 `0.001`초 근처의 값이다. 이건 실제 OCR/표인식 시간이 아니다.

- Docling은 `converter.convert(pdf_path)` **한 번 호출로 PDF 전체를 통째로 처리**한다 (페이지 단위로 쪼개서 돌리지 않음).
- `summary.json`의 `seconds`는 그 결과를 페이지별 `pNNN.txt` 파일로 **나눠 쓰는 시간**만 잰 것이라 사실상 0에 가깝다.
- **진짜 처리 시간은 문서 단위로만 있다**: `config.json`의 `"seconds"` (예: T21-025 전체 10페이지 = 9초).
- version9/version12처럼 페이지마다 따로 OCR을 돌리는 방식과 달리, version11은 구조상 페이지별 시간을 잴 수 없다. 필요하면 PDF를 1페이지짜리로 잘라서 `convert()`를 페이지마다 호출해야 하는데, 이 경우 Docling의 문서 전체 레이아웃 분석 이점이 줄어들어 전체 속도가 느려질 수 있다.

## 한계 (version12를 만든 이유)

- TableFormer는 **테두리/격자선이 뚜렷한 표**는 잘 인식하지만, 테두리 없이 공백/들여쓰기로만 구분된 표(예: T21-002 4항 응급조치 요령)는 레이아웃 모델이 "표"로 인식하지 못하고 일반 본문 읽기 순서로 풀어버림 → 이런 페이지는 `|` 구조가 통째로 사라져서 version9(좌표 기반 행 묶기)보다 결과가 더 나쁨.
- 이 한계 때문에 "본문은 version9, 표만 Docling"으로 역할을 나눈 [[version12]](2026-10-29_version12_방법정리.md)을 만들었음.
