# B. 판정·저장 부분 설계: 2차 평가 → 판정 검수 → 저장

작성 2026-11-02 · 상태: 승인 전 · 개요와 약속은 `2026-11-02-backend-pipeline-design.md`

기준 자료: 정합성검증 개발설계서 **v0.4**, 규칙표 **v0.3**, Msds-test_v0.4, HTODB (개요 1절). 아래 장 번호는 v0.4 슬라이드 번호다.
A와는 개요 6절의 넘김 기록으로만 이어진다. B는 A 없이 넘김 기록만 있으면 돈다.

## 1. 맡는 일

설계서 v0.4 "전체 처리 FLOW"(9장)의 ①~⑧ 중 ① 입력 정리부터 ⑧ 저장·화면까지. 추출(AI 서버 ①)과 근거 재확인(⑦⑧ 메시지)은 맡지 않는다.

```
넘김 기록 → ① 입력 정리 → ② 단일/혼합 판별 → ③ 2항 검증 · ④ 15항 검증 → ⑤ 공통 검증 → ⑥ 판정 집계
          → (판정 버전 저장, 화면에 바로 보임) → ⑦ 설명 생성 (불일치·경계·근거부족만, 모델 창구 뒤쪽)
          → [사람] 판정 검수 → [사람] 저장 → 저장본
```

설계서 메시지 ⑦⑧(엔진이 추출 서버에 근거 재확인 요청)은 이 PoC에서 하지 않는다. B가 A를 부르지 않는다는 약속 때문이다 (Claude 판단). 입력이 비면 근거부족으로 판정하고, 사람이 추출값 탭에서 고치면 넘김②로 다시 판정한다.

## 2. 판정 원칙 (설계서 v0.4 "설계 원칙"·"안전장치")
- **판정은 규칙엔진**. 상태가 없고, 같은 입력이면 같은 결과다. 법령 값은 코드가 아니라 규칙표(`rules/`)와 HTODB에만 둔다.
- **AI는 설명만**. 불일치·경계·근거부족 판정만 finding + trace + evidence를 묶어 보낸다 (14장 요청·응답 예시).
- 안전장치: 응답의 판정·구분 값은 무시, 설명 속 숫자·코드가 trace·evidence에 모두 있는지 검사, JSON Schema 출력·temperature 0, 실패 시 1회 재요청 후 규칙별 템플릿 문장으로 대체하고 표시.
- 판정 4종(일치·불일치·경계·근거부족)과 불일치 유형·심각도는 "판정 체계와 심각도"(8장) 그대로.

## 3. 지식과 로직: 최신 자료로 다시 맞춘다

지금 `compliance/`(`single.py`, `sec15.py`, `knowledge.py`, `classifier.py`)는 "설계서 v0.2가 없어 팀 결정으로 정했다"는 가정 위에 있다. 다음으로 맞춘다.

- **지식 원천**: HTODB 16개 테이블만 (D-01, D-02, D-03 확정 10-27). 엑셀 7종 전제는 버린다. 로컬 적재본(`deploy/htodb/`, `htodb` 스키마)과 조회 코드(`compliance/htodb/repo.py`)를 쓴다.
- **지식 제공자 함수**: 설계서 v0.4 "지식 분리 인터페이스"(15장)의 3개 함수 `get_reference(cas, as_of)`, `get_regulation(cas, content, as_of)`, `classify_mixture(components, props, tests, as_of)`. 공통 규약(값 없음 → status '없음' → 근거부족, 시스템 오류 → '근거부족(시스템)', 모든 응답에 source·knowledge_version·as_of)도 그대로.
- **분류 로직**: Msds-test_v0.4의 `ghsclass` 구조를 따른다. 끼움 자리 두 개 — `ReferenceProvider`(지금 `to21_csv` → HTODB 직접 조회) · `ClassificationLogic`(지금 `to21_v6` → 나중 `to21_api`)를 `config.yaml` 한 줄로 바꾼다. 15장의 3개 함수는 이 두 자리 위에 얹는다 (Claude 판단. 설계서와 실습 코드가 둘 다 TO21 자료라 둘 다 지킨다).
- **규칙표**: v0.3 (`class_map`·`reg_map` 코드 기준, `assumptions.yaml`에 D-21~24, `rules_check.py --db`로 HTODB 대조).
- **v0.4 결정사항 반영**: D-04(같은 경로 독성값 여러 개면 최저값), D-05(환경부 KR02 → 고용노동부 KR03), D-07(M계수 DB 수생독성으로 산출), D-11(위험물 DB 류·품명·지정수량과 9항 인화점 대조), D-12(부등호 처리), D-15·16(한계농도), D-17(물리적 위험성 순서), D-18(구분5는 참고), D-19(pH), D-20(고시 제2026-26호), D-21~24(DB 파싱, 흡입 형태 재지정, 동점도, UN 보충표 `un_info.csv`).
- **v0.4 미결사항**(53장)은 표시된 가정으로 개발하고, 가정을 썼다는 사실을 trace의 `assumptions`에 남긴다.
- **입력**: 넘김 기록의 `extraction`(추출스키마 v0.6)을 "입력 데이터 매핑"(17장, v0.5 기준)대로 읽는다. v0.6은 v0.5와 하위 호환이다 (작업기록 2026-10-26).

## 4. 언제 판정하나
- 새 넘김 기록이 들어오면 바로 판정한다 (사용자 결정: 검증 직후 미리). 판정 작업자는 `judge` 스키마 대기열에서 `SKIP LOCKED`로 가져간다. 판정은 모델을 쓰지 않아 금방 끝나므로 화면을 열면 이미 있다.
- 판정 키 = `extraction_sha256` + `as_of` + engine_version + knowledge(provider·version) + rule_tables 버전. 같은 키가 있으면 다시 계산하지 않는다.
- 설명은 판정이 저장된 뒤 따로 만든다. 다 안 나와도 판정은 볼 수 있고 설명 자리는 "작성 중". 설명은 finding의 입력(판정·trace·evidence)이 바뀐 항목만 다시 만들고, 바뀌지 않은 항목은 이전 설명을 쓴다 (Claude 판단).

## 5. 저장: 덮어쓰지 않고 쌓는다
- **판정 버전**: 넘김 기록 하나(또는 버전 변경)마다 판정 버전 하나. 이전 버전은 지우지 않는다. 화면은 최신 버전을 보인다. 결과 모양은 "결과 구조 (consistency 블록)"(45장)을 따르되, `findings[].review`는 판정 버전 안에 쓰지 않는다 (아래).
- **판정 검토는 별도 이벤트**: "불일치 확정·예외 승인·의견"(설계서 메시지 ⑭)은 판정 버전과 따로 쌓는다. finding ID를 버전과 무관하게 고정해서(2항: `class_code`+`route_form`, 15항: 성분×`law`×`item_code`) 새 버전에서도 같은 항목의 이전 검토 이력을 이어 보인다. 화면에 보일 때만 consistency 블록의 `review` 자리에 합쳐 넣는다.
- **저장본 ("4. 저장")**: 사람이 저장을 누르면 그 순간의 넘김 기록 번호·판정 버전·판정 검토 상태(미검토 포함)를 가리키는 저장본을 만든다. 처리 안 된 판정이 남아도 막지 않는다 (프론트엔드 `save-guard-dialog.tsx`). 다시 저장하면 새 저장본이 생기고 이전 것은 남는다. 화면의 "저장됨"과 리포트·PDF 출력은 최신 저장본을 쓴다 (Claude 판단).
- **기록 필드**: 판정 버전마다 engine_version, knowledge.provider/version, rule_tables, as_of, msds_revision_date (16장 "기록 필드").
- 판정 버전 + 판정 검토 + 저장본 만들기는 각각 한 트랜잭션.

## 6. API (B의 라우터)
- 판정 보기 (최신 버전, 또는 버전 지정): 2항 요약, 15항, 불일치 상세(trace), 성분별 요약 — 설계서 화면 예시 ①~④.
- 판정 버전 목록과 버전 간 차이.
- 판정 검토 남기기 (확정·예외 승인·의견).
- 저장 (저장본 만들기), 저장본 보기·리포트 내려받기.
- 시험용: 넘김 기록을 직접 넣기 (A 없이 돌리기 위해. 운영에서는 끈다).

## 7. 완료 기준 (설계서 v0.4 "단계별 개발 순서"·"테스트 케이스"·"평가 방법"에서)
- 정답 예제 25번 황산을 넘김 기록으로 넣으면 판정·설명·저장까지 돈다 (A 없이).
- 단위 테스트: 경구 ATEmix 300 / 300.1 / 2,000 / 2,000.1, 계산 예제 3건, 함량 범위 경계, "10% 이상" vs "초과" 경계, 인화점 22℃·61℃.
- 적합성 테스트: 지식 제공자 응답 형식·값 없음·시간 초과·버전 필드.
- e2e: 25번 2·15항 판정 목록이 고정본과 같다. 오류 주입(피부 부식성 삭제, 사고대비물질 삭제)을 과소분류(높음)·누락(높음)으로 잡는다.
- **같은 넘김 기록 2회 → 판정 완전히 같다** (설명 제외).
- 설명 숫자 환각 0건 (검사에 걸린 건은 템플릿 문장).
- 추출값 수정으로 새 넘김 기록 → 새 판정 버전, 이전 버전과 판정 검토 이력 남음.
- 미검토가 남아도 저장되고, 저장본이 그 상태를 가리킨다.

## 8. 구현하는 사람에게 맡기는 것
- `judge` 스키마 표 세부, 판정 작업자 구현, 설명 프롬프트 문구와 템플릿 문장.
- 설계서 v0.4 개발 순서(48장) 안에서의 작업 쪼개기.
