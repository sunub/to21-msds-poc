# A. 추출 부분 설계: 업로드 → 추출 → 검증 → 추출값 검수

작성 2026-11-02 · 상태: 승인 전 · 개요와 약속은 `2026-11-02-backend-pipeline-design.md`

기준 자료: TO21 추출 작업가이드 v0.6과 v0.6 도구 일체 (개요 1절). B와는 개요 6절의 넘김 기록으로만 이어진다.

## 1. 맡는 일

작업가이드 v0.6 "AI 모델 운영 시 전체 시스템 구성도"의 ①~⑤를 맡는다.

| 가이드 단계 | A에서 | 지금 코드 |
|---|---|---|
| ① 전처리: 텍스트층 추출·판별, 쪽 이미지 | 그대로 | `preprocess/render.py` |
| ② 항목 분할: 16개 항 경계, 다중 MSDS 분리 | 그대로 | `preprocess/section_contract.py` |
| ③ 추출 엔진: JSON 스키마 강제 출력 | 추출 대상 9개 항(1·2·3·8·9·11·12·14·15) | `extract/section_runner.py` (커밋 5624a0d) |
| ④ 정규화·검증: R01~R26, V01~V23, **오류 항목만 재추출** | 검증 + 오류 항만 재추출 | `checks/validator.py`, `checks/source_match.py` |
| ⑤ 사람 검토 | 추출값 확인 (화면 2.1·2.2), 사람이 고름 | `service/review.py` |
| ⑥ MSDS DB | A의 `extract` 스키마 + 넘김 기록 | `service/store.py` (파일) → PostgreSQL |

가이드 ⑤는 "필수 항목 신뢰도 0.9 미만은 사람 검토"를 예로 든다. 이 서비스는 검토 여부를 사람이 고른다 (사용자 결정). 신뢰도 낮은 칸·검증 오류 칸은 화면에 "검토 필요"로 표시만 한다.

## 2. 흐름과 상태

```
업로드 → [전처리 대기열] → 전처리(CPU) → 항목 분할 → [추출 대기열] → 추출(모델) → 검증
      → (오류 항만 재추출, 최대 1회) → 넘김① → 검수 대기
      → [사람] 방식 선택 → (추출값 확인·수정 → 넘김②) / (판정 바로 가기)
```

- 자동 구간 상태: `queued → running(stage) → done | failed | interrupted`. 단계는 지금 `service/progress.py`의 `preprocess → sections → extract → finalize`에 `checks`를 더한다. `done`은 넘김①을 남겼다는 뜻이다.
- 사람 구간 상태: `검수 대기 → 추출값 확인 중 → 판정으로 넘김`. 화면이 어디서 이어 열지 정하는 데 쓴다. 판정 검수·저장 상태는 B가 가진다.

## 3. 대기열

- 대기열과 작업 상태는 `extract` 스키마의 표에 둔다. 작업자는 `SELECT … FOR UPDATE SKIP LOCKED`로 다음 작업을 가져간다. 작업자를 여럿 띄워도 한 작업을 두 번 잡지 않는다.
- 전처리(CPU)와 추출(모델)은 줄을 따로 세운다. 한 문서가 모델을 기다리는 동안 다음 문서의 전처리를 끝내 둔다.
- 모델 호출은 공용 모델 창구를 지난다 (개요 5절). 지금은 문서마다 `concurrency: 16`이라 동시 문서 수만큼 늘어난다.
- 서버가 다시 켜지면 `running`이던 작업은 `interrupted`로 바꾸고 대기열 앞에 다시 넣는다 (지금 `store.recover`와 같은 뜻).
- 재시도: 모델 호출 실패는 호출 단위(`run.max_retries`). 작업 전체 실패는 자동 1회, 그래도 실패하면 `failed`로 두고 사람이 다시 돌린다 (지금 `/retry`).
- 화면에 대기 순번과 예상 시간을 보인다.

## 4. 동시에 몇 건을 추출할지: 실험으로 정한다

결과 일관성이 30분 목표보다 우선이다 (사용자 결정). vLLM은 temperature 0이어도 함께 배치되는 요청에 따라 출력이 미세하게 달라질 수 있다.

1. 같은 문서를 **혼자** 두 번 돌려 자연적인 차이를 잰다 (문서 안에서 이미 9개 항을 동시에 부르므로 0이 아닐 수 있다).
2. 같은 문서를 다른 문서 1·2·4건과 **함께** 돌려 차이를 잰다.
3. 비교는 TO21 채점기 v0.6 기준 칸 단위. 서로 다른 양식 3건 이상, 스캔본 1건 포함.
4. 차이가 1의 기준을 넘지 않는 가장 큰 N을 운영값으로 쓰고 설정 파일에 둔다.
5. 같은 실험에서 11쪽 문서 291초(실측) 중 전처리·모델 호출이 각각 얼마인지 잰다.
6. 결과를 ADR로 남긴다.

N=1이면 20건에 약 1시간 30분이 걸려 30분을 못 지킨다. 그때는 예상 시간을 정직하게 보이고 측정값을 남긴다.

## 5. 같은 파일의 추출 재사용

- 같은 파일(sha256)이고 추출 설정 키가 같으면 추출을 다시 하지 않고 이전 추출 결과를 복사해 새 작업을 시작한다. 지금 `duplicate_of`를 기록만 하는 것을 재사용으로 넓힌다.
- 추출 설정 키 = 모델 태그 + `models.yaml`의 그 모델 항목 + 코드 커밋 + TO21 스키마·동의어사전 버전 (Claude 판단. 프롬프트를 바꾸면 재사용하지 않는다).
- 재사용하는 것은 추출 결과뿐이다. 검수는 작업마다 처음부터 따로 한다 (사용자 결정).
- 재사용은 일관성을 대신하지 않는다. 4절 실험과 "두 번 넣기" 시험은 재사용을 끄고 한다.

## 6. 검증 (작업가이드 ④)

- TO21 검증기 V01~V23과 원문 대조를 돌린다. 모델을 부르지 않으므로 대기열 없이 추출 직후 실행한다.
- 검증 오류가 난 항만 한 번 다시 추출한다 (가이드 "오류 항목만 재추출"). 그래도 오류면 그대로 두고 "검토 필요"로 표시한다. 재추출도 모델 창구를 지난다.
- 결과는 넘김 기록의 `checks`로 B에 간다.

## 7. 추출값 검수와 저장

- **추출 결과는 고치지 않는다.** 사람의 수정은 검수 기록(원래 값·고친 값·근거·검토자·시각)에 따로 쌓는다. 지금 `service/review.py` 방식 그대로다. 넘김 기록의 `extraction`은 수정분을 얹은 값(`review.apply_edits`)이다.
- **넘김②를 보내는 때**: 추출값 확인을 마치고 판정으로 넘어갈 때 한 번. 판정 검수 화면의 추출값 탭에서 고치면 고칠 때마다. 추출값 확인 화면에서는 고칠 때마다 보내지 않는다 (Claude 판단).
- **다시 추출할 때**: 추출을 처음부터 다시 돌리면 칸이 달라질 수 있다. 이전 검수 기록은 지우지 않고 "이전 실행의 기록"으로 남겨 화면에서 볼 수 있게 한다 (지금 `_set_aside_review`의 방식).
- **재생성**: TO21 `DB적재_재생성_v0.6.py`가 그대로 돌게 한다. 원래 추출값과 수정분을 얹은 값 둘 다 재생성할 수 있어야 한다 (화면은 수정분을 얹은 값).
- `state.json`, `review.json`은 `extract` 스키마로 옮긴다. 원본 PDF와 쪽 이미지는 지금처럼 파일로 둔다.

## 8. API (A의 라우터)

지금 `api/extract_app.py`의 경로(업로드, 목록, 상세, 쪽 이미지·줄, 결과, 항별 결과, 재생성, 검수 보기·칸 수정·항 확인, 다시 돌리기)를 유지한다. 더할 것:
- 대기 순번·예상 시간 (목록과 상세에)
- "판정으로 넘기기" (넘김②를 만든다)

## 9. 완료 기준
- 4절 실험을 했고 N과 측정값이 ADR에 있다.
- 20건을 한 번에 넣으면 모두 넘김①을 남기거나 이유가 남은 `failed`로 끝나고, 걸린 시간이 기록된다.
- 처리 중 서버를 껐다 켜도 작업이 이어진다. 작업자 프로세스 2개를 띄워도 한 작업을 두 번 처리하지 않는다.
- 같은 문서를 재사용 끄고 두 번 넣으면 넘김 기록의 `extraction`이 4절 기준 안에서 같다.
- 추출값을 고치면 새 넘김 기록이 생기고, 이전 넘김 기록과 검수 기록은 남는다.
- B 없이도 시험이 모두 돈다.

## 10. 구현하는 사람에게 맡기는 것
- `extract` 스키마 표 세부, 마이그레이션 도구, 작업자 구현(스레드/프로세스), 모델 창구 구현.
- 예상 대기 시간 계산 방식.
