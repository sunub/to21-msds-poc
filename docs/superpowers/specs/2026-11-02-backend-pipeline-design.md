# 백엔드 처리 흐름 설계 (개요 · 두 부분 사이의 약속)

작성 2026-11-02 · 상태: 승인 전 · 최신 TO21 자료 기준으로 다시 씀

이 문서는 전체 그림과 두 부분이 주고받는 약속만 담는다. 각 부분의 설계는 따로 있다.

- **A. 추출 부분**: 업로드부터 추출값 검수까지 → `2026-11-02-part-a-extraction-design.md`
- **B. 판정·저장 부분**: 2차 평가부터 저장까지 → `2026-11-02-part-b-judgment-save-design.md`

두 부분은 6절의 약속만 지키면 서로 모른 채 따로 만들고, 따로 시험하고, 따로 배포할 수 있다 (결정).

## 2. 왜 하는가

지금 서비스(`backend/src/msds/service/`)는 한 사람이 PDF를 한 건씩 올리는 시연을 전제로 만들어졌다. 대기열은 메모리에 있어 서버를 다시 켜면 사라지고, 진행 상태는 문서마다 `state.json` 파일로 둔다. 2차 평가는 추출 흐름에 붙어 있지 않고, `compliance/` 코드는 설계서 v0.2도 없던 때의 가정으로 짜여 있다.

PoC 시연에서 여러 사람이 동시에 MSDS를 올리고, 추출부터 저장까지 이어지게 한다. 가장 중요한 것은 **같은 입력이면 언제 누가 돌려도 같은 결과**다 (설계서 v0.4 평가 지표 "재현성 0건", 테스트 "같은 입력 2회 실행 → 결과 완전히 같음(LLM 설명 제외)").

## 3. 전체 흐름

```
┌───────────────────── A. 추출 부분 ─────────────────────┐    ┌───────────── B. 판정·저장 부분 ─────────────┐
 업로드 → 전처리 → 항목 분할 → 추출 → 정규화·검증 ──(넘김①)───────▶ 2차 평가 (미리 판정)
                                     │                    │        판정: 규칙엔진 / 설명: 모델
                    [사람] 검수 방식 선택 (화면 2.1)          │              │
                                     │                    │    [사람] 판정 검수 (2.3 2항 · 2.4 15항)
                    [사람] 추출값 확인·수정 (2.2, 선택) ─(넘김②)─▶ 다시 판정 → 새 판정 버전
                                                          │              │
                                                          │    [사람] 저장 (3.1~3.2) → 저장본
└─────────────────────────────────────────────────────────┘    └──────────────────────────────────────────────┘
              모델 호출 창구 (서버 전체 동시 호출 상한 하나): A의 추출과 B의 설명이 함께 거친다
```

- 자동 구간: A의 추출·검증, B의 2차 평가(검증이 끝나자마자 미리 판정, 결정).
- 사람 구간: 검수 방식 선택 → 추출값 확인(선택) → 판정 검수 → 저장. 추출값 확인 여부는 사람이 고르고, 입력 유형(텍스트층)으로 권장만 표시한다 (결정, 프론트엔드 `app/review/mode/page.tsx`).
- 판정 검수 화면의 추출값 탭에서 값을 고쳐도 그 수정은 A가 받고, A가 넘김②를 다시 보낸다.

## 4. 목표 · 하지 않을 것 · 실패로 볼 것

**목표**
- 사용자 10명, 대기열 최대 20건을 견딘다 (결정).
- 마지막으로 올린 문서까지 30분 안 (목표치). **결과 일관성이 30분보다 우선한다** (결정).
- 서버가 다시 켜져도 대기·진행 중이던 작업을 잃지 않는다.
- A와 B를 따로 만들고 따로 시험할 수 있다. B는 A 없이 정답 예제(`추출예제_25_황산_v0.6.json`)만으로 끝까지 돈다.

**하지 않을 것**
- 운영 규모 큐 시스템 (Redis·Celery 같은 별도 서버).
- TO21이 우리 DB를 직접 읽는 연동. DB는 우리 화면만 쓴다 (결정).
- 설계서 v0.4 "검증 범위"(2항·15항) 밖의 판정, 그리고 v0.4가 PoC 제외로 둔 것: 구버전 판정(D-09), 화합물군 합산(D-10), 8항 노출기준 값, 해외 규제, 브리징.

**실패로 볼 것 (돌아가도 실패)**
- 같은 입력(같은 추출값·같은 기준일·같은 버전)인데 판정이 다르다 (설명 문장 제외).
- 검수자가 고친 값이나 검토 이력이 다시 실행하면서 지워지거나, 남아 있어도 화면에서 찾을 수 없다. (항상 이어받으라는 뜻은 아니다. 추출을 처음부터 다시 돌려 칸이 달라지면 "이전 실행의 기록"으로 남기고 그 사실을 보인다.)
- AI 설명이 엔진 판정과 다른 구분·숫자를 말하는데 그대로 화면에 나간다.
- B를 고치려면 A 코드를 알아야 한다 (또는 그 반대).

## 5. 공통 기반

- **DB**: 이미 쓰고 있는 PostgreSQL 16 (`deploy/htodb/compose.yaml`, 백엔드는 `psycopg`·`psycopg-pool` 사용) (결정). 한 서버 안에서 스키마를 나눈다.
  - `extract` 스키마: A만 쓴다.
  - `judge` 스키마: B만 쓴다.
  - `htodb` 스키마: 지식DB. B가 읽기 전용 계정 `kdb_reader`로만 읽는다 (지금 그대로).
  - 부분마다 쓰기 계정을 따로 둔다. A 계정은 `judge`에, B 계정은 `extract`에 쓸 수 없다 (Claude 판단. 섞이지 않게 DB가 막는다).
- **작업 번호**: 지금의 문서 번호 `U-<날짜>-<순번>`. A가 만들고 B는 받아서 쓴다. 검수 기록·판정·저장본은 모두 작업 번호에 묶는다. 같은 PDF라도 작업마다 처음부터 따로 검수한다 (결정).
- **모델 호출 창구**: 서버 전체에서 모델로 나가는 동시 호출 수의 상한 하나. 빈자리는 A의 추출이 먼저 가져가고 B의 설명이 뒤에 선다 (Claude 판단). 창구는 두 부분이 같이 쓰는 작은 공용 모듈이며 어느 부분의 내부도 알지 않는다.
- **대상 모델**: 서비스 기본값 `qwen36_35b_runpod` (RunPod vLLM). B의 설명도 같은 모델 (Claude 판단. 설계서 v0.4 미결 10 "설명 LLM 모델·서버 사양"이 정해지면 바꾼다).

## 6. A → B 약속 (넘김)

A와 B가 주고받는 것은 이것뿐이다. B는 A의 표·코드·파일 경로를 읽지 않는다.

### 6.1 넘김 기록
A는 "판정해도 되는 추출값"이 생길 때마다 하나 만든다: 추출·검증이 끝났을 때(넘김①), 추출값 확인을 마치고 판정으로 넘어갈 때와 판정 검수 중 추출값을 고쳤을 때(넘김②).

| 칸 | 내용 |
|---|---|
| `job_id` | 작업 번호 |
| `handoff_seq` | 그 작업 안에서 1부터 늘어나는 번호. B는 가장 큰 번호를 최신으로 본다 |
| `extraction` | TO21 추출스키마 **v0.6**에 맞는 JSON 전체. 검수 수정분을 이미 얹은 값 |
| `extraction_sha256` | 위 JSON의 해시 (키를 정렬해 직렬화). B의 재계산 판단 키 |
| `checks` | 검증 결과: TO21 검증기 V01~V23 오류·경고, 원문 대조에 실패한 칸 경로 |
| `field_status` | 칸 경로별 `미검수 / 확인함 / 수정됨` (화면 2.2 표시. B는 판정 근거 표시에만 씀) |
| `evidence` | 칸 경로별 원문 쪽·조각 (B의 설명 요청에 쓴다) |
| `as_of` | 판정 기준일. 업로드 때 받은 값, 없으면 업로드한 날 (설계서 v0.4 메시지 명세 ①) |
| `meta` | 원본 파일 이름, 쪽 수, 텍스트층 판정, 추출 설정 키(모델·코드 커밋·스키마 버전) |
| `created_at` | 만든 시각 |

`msds_revision_date`처럼 판정에 필요한 다른 값은 B가 `extraction` 안(설계서 v0.4 "입력 데이터 매핑")에서 직접 읽는다.

### 6.2 전달 방식 (PoC)
- A가 `extract.handoff` 표에 한 줄을 넣는다 (A의 상태 변경과 같은 트랜잭션). B는 이 표 하나에만 읽기 권한을 받아 새 줄을 가져가 판정한다 (Claude 판단).
- 한 줄은 쓴 뒤 바꾸지 않는다. 고칠 일이 생기면 `handoff_seq`가 하나 큰 새 줄을 넣는다.
- B는 같은 `extraction_sha256` + 같은 `as_of` + 같은 버전(엔진·지식·규칙표)을 이미 판정했으면 다시 계산하지 않는다.
- 나중에 두 부분을 다른 서버로 나누면 이 표 대신 HTTP로 같은 JSON을 보낸다. 내용은 그대로다.

### 6.3 화면과의 관계
- 화면은 A의 API(업로드·진행·추출값·검수)와 B의 API(판정·설명·판정 검수·저장)를 따로 부른다. PoC에서는 같은 FastAPI 앱에 라우터 두 개로 붙인다 (Claude 판단). 따로 띄워도 된다.
- B는 A에게 아무것도 요청하지 않는다. 판정 검수 중 추출값을 고치는 것은 화면이 A의 API를 부르는 것이다.

## 7. 공통 완료 기준
- A 없이 B: 정답 예제 `추출예제_25_황산_v0.6.json`을 넘김 기록으로 넣으면 B가 판정·설명·저장까지 돈다.
- B 없이 A: 20건을 넣으면 모두 넘김 기록을 남기거나 이유가 남은 `failed`로 끝난다.
- 둘을 붙여서: 업로드 → 판정 화면 → 추출값 수정 → 새 판정 버전 → 저장까지 한 번에 된다.
