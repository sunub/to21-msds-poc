# 백엔드 처리 흐름 설계: 대기열 · 검증 · 2차 평가 · 저장

작성 2026-11-02 · 상태: 논의 결과 정리 (승인 전)

## 1. 왜 하는가

지금 서비스(`backend/src/msds/service/`)는 한 사람이 PDF를 한 건씩 올리는 시연을 전제로 만들어졌다.
대기열은 메모리에 있어 서버를 다시 켜면 사라지고, 진행 상태는 문서마다 `state.json` 파일로 둔다.
2차 평가(정합성 판정)는 추출 흐름에 붙어 있지 않다.

PoC 시연에서 여러 사람이 동시에 MSDS를 올린다. 추출 → 검증 → 2차 평가(미리 판정)는 자동으로 돌고, 그 뒤는 프론트엔드가 이미 정한 사람의 흐름
(검수 방식 선택 → 추출값 확인(선택) → 판정 검수 → 저장)을 백엔드가 받쳐 준다.
이때 가장 중요한 것은 **같은 문서는 언제 누가 올려도 같은 결과가 나오는 것**이다.

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

**목표**
- 사용자 10명이 쓰고 대기열에 최대 20건이 쌓이는 상황을 견딘다.
- 업로드한 문서는 추출 → 검증 → 2차 평가까지 사람 손 없이 이어진다. 사람이 판정 화면을 열 때 판정이 이미 있다. 검수와 저장은 사람의 선택으로 진행된다 (3절).
- 서버가 다시 켜져도 대기 중·진행 중이던 작업을 잃지 않는다.
- 마지막으로 올린 문서가 결과를 받을 때까지 30분 안 (목표치. 4절의 일관성이 우선한다).

**하지 않을 것**
- 운영 규모(수백 명, 여러 서버)의 큐 시스템. Redis·Celery 같은 별도 서버를 들이지 않는다.
- TO21이 DB를 직접 읽는 연동. DB는 우리 화면만 쓴다.
- 2차 평가 범위 확장 (2항·15항 이외). TO21 정합성검증 개발설계서 **v0.4**(이 문서가 기준) 6장의 범위를 따른다.

**실패로 볼 것 (돌아가도 실패)**
- 같은 문서를 다시 올렸는데 판정 결과가 달라진다 (설명 문장 제외).
- 검수자가 고친 값이나 검토 이력이 다시 실행하면서 지워지거나, 남아 있어도 화면에서 찾을 수 없게 된다.
  (항상 이어받으라는 뜻은 아니다. 추출을 처음부터 다시 돌리면 칸이 달라져 그대로 얹을 수 없을 수 있다. 그때는 "이전 실행의 기록"으로 남기고 그 사실을 보인다. 지금 `service/store.py`의 `_set_aside_review`가 하는 방식.)
- AI 설명이 엔진 판정과 다른 구분·숫자를 말하는데 그대로 화면에 나간다.

## 3. 전체 흐름

```
업로드 ─▶ [전처리 대기열] ─▶ 전처리 (CPU) ─▶ [추출 대기열] ─▶ 1. 추출 (모델) ─▶ 2. 검증 (모델 없음) ─▶ 3. 2차 평가 (미리 판정)   ← 자동
                                                                                      │
                                                                                      ▼
                                                         [사람] 검수 방식 선택 (화면 2.1)
                                                    입력 유형으로 권장만 표시하고, 사람이 고른다
                                                      │                                │
                                          "추출값 확인부터 하기"               "판정으로 바로 가기"
                                                      │                                │
                                     [사람] 추출값 확인·수정 (2.2)                      │
                                                      └───────────────┬────────────────┘
                                                                      ▼
                                   (추출값을 고쳤으면 3. 2차 평가를 다시 돌려 새 판정 버전)
                                                                      ▼
                                                     [사람] 판정 검수 (2.3 2항, 2.4 15항)
                                                                      ▼
                                                     [사람] 저장 (3.1~3.2) → 4. 저장 (확정본)

모델 호출 창구 (서버 전체 동시 호출 상한 하나): 추출과 설명이 함께 거친다
```

- 모든 작업은 작업 번호(지금의 문서 번호 `U-<날짜>-<순번>`)로 끝까지 추적한다.
- **추출값 확인을 할지는 사람이 고른다** (결정. 프론트엔드 `app/review/mode/page.tsx`). 백엔드는 텍스트층 판정(`정상`이면 판정 바로 가기, `없음`·`글꼴깨짐`·`혼합`·판정 못함이면 추출값 확인 권장)으로 권장만 준다. 알고리즘이 관문을 정하지 않는다.
- 건너뛴 추출값은 "미검수"로 남고, 판정 검수 중에도 추출값 탭에서 언제든 확인·수정할 수 있다.
- **2차 평가는 검증이 끝나자마자 미리 돈다** (결정). 판정 화면을 열면 바로 보이게 하기 위해서다. 판정은 규칙엔진이라 금방 끝나고, 설명은 모델 창구에서 추출보다 뒤에 선다.
- 추출값을 고치면(추출값 확인 중이든 판정 검수 중이든) 그 값으로 다시 판정해 새 판정 버전을 만든다 (7절). 설명은 판정 항목의 입력(판정·trace·근거)이 바뀐 것만 다시 만들고, 바뀌지 않은 항목은 이전 설명을 쓴다 (Claude 판단. 모델 호출을 아끼고 설명이 흔들리지 않게).
- 추출값 확인 중에는 고칠 때마다 다시 판정하지 않고, 판정 화면으로 넘어갈 때 한 번 다시 판정한다. 판정 검수 중에 고치면 바로 다시 판정한다 (Claude 판단).
- **저장은 사람이 누를 때만** 한다. 처리하지 않은 판정이 남아도 막지 않고 "미검토로 두고 저장"할 수 있다 (프론트엔드 `components/review/save-guard-dialog.tsx`).

## 4. 1단계 추출과 대기열

### 4.1 결정 사항
- **결과 일관성이 30분 목표보다 우선한다** (결정).
- 대기열과 작업 상태는 **PostgreSQL**(7.2절)에 둔다. 메모리 `queue.Queue`를 대신한다. 작업자는 `SELECT … FOR UPDATE SKIP LOCKED`로 다음 작업을 가져가, 작업자가 여럿이어도 한 작업을 두 번 잡지 않는다.
- 전처리(쪽 이미지·텍스트층·OCR)와 모델 추출은 줄을 따로 세운다. 한 문서가 모델을 기다리는 동안 다음 문서의 전처리를 끝내 둔다.
- 모델로 나가는 모든 호출은 **창구 하나**를 지난다. 창구는 서버 전체의 동시 호출 수 상한을 지킨다
  (지금은 문서마다 `concurrency: 16`이라 문서 수만큼 늘어난다). 2차 평가의 설명 호출도 같은 창구를 쓰되, 빈 자리가 있을 때 추출이 먼저 가져간다 (설명은 짧고 사용자를 막지 않으므로. Claude 판단).
- 대상 모델은 지금 서비스 기본값 `qwen36_35b_runpod`(RunPod vLLM, `service/pipeline.py`의 DEFAULT_MODEL_TAG)이고, 설명도 같은 모델이 쓴다. 4.2 실험도 이 모델로만 잰다 (Claude 판단). 모델을 바꾸면 실험을 다시 한다.
- 같은 파일(sha256)과 같은 추출 설정이면 추출을 다시 하지 않고 이전 결과를 쓴다. 지금 `duplicate_of`를 기록만 하는 것을 재사용으로 넓힌다. 추출 설정 = 모델 태그 + `models.yaml`의 그 모델 항목 + 코드 커밋 + TO21 스키마 버전 (프롬프트를 바꾸면 재사용하지 않게. Claude 판단).
- 재사용하는 것은 추출 결과뿐이다. 검수 수정과 판정 검토는 **작업마다 처음부터 따로** 한다 (결정). 같은 PDF를 두 사람이 올리면 두 작업은 같은 추출 결과에서 출발하지만, 검수와 그 뒤의 판정 버전은 서로 섞이지 않는다.
- 재사용은 일관성을 대신하지 않는다. 4.2 실험과 9절의 "두 번 넣기" 시험은 재사용을 끄고 한다.
- 화면에 대기 순번과 예상 시간을 보여준다.

### 4.2 동시에 몇 건을 추출할지: 실험으로 정한다
vLLM은 temperature 0이어도 함께 배치되는 요청에 따라 출력이 미세하게 달라질 수 있다.
문서를 동시에 몇 건 추출할지(N)는 아래 실험으로 정하고 결과를 ADR로 남긴다.

1. 기준 잡기: 같은 문서를 **혼자** 두 번 돌려 자연적인 차이를 잰다 (문서 안에서 이미 추출 대상 9개 항(1·2·3·8·9·11·12·14·15, 커밋 5624a0d)을 동시에 부르므로 0이 아닐 수 있다).
2. 같은 문서를 다른 문서 1·2·4건과 **함께** 돌려 차이를 잰다.
3. 비교는 TO21 채점기(`TO21_MSDS_채점기_v0.6.py`) 기준 칸 단위로 한다. 문서는 서로 다른 양식 3건 이상.
4. 차이가 1의 기준을 넘지 않는 가장 큰 N을 운영값으로 쓴다. 설정 파일에서 바꿀 수 있게 둔다.
5. 같은 실험에서 291초(11쪽 문서 실측) 중 전처리와 모델 호출이 각각 얼마인지도 잰다.

N=1로 정해지면 20건에 약 1시간 30분이 걸려 30분을 지키지 못한다. 그때는 예상 시간을 화면에 정직하게 보이고 측정값을 문서에 남긴다.

### 4.3 작업 상태
`queued → running(stage) → done | failed | interrupted`. 지금 `service/progress.py`의 상태와 단계를 유지하고 단계에 `checks`, `compliance`를 더한다. 이 상태는 자동 구간(추출·검증·2차 평가)의 것이다. 설명 생성은 판정이 끝난 뒤 따로 이어지며, 설명이 다 나오지 않아도 작업은 `done`이고 판정은 볼 수 있다 (설명 자리에 "작성 중").
사람 구간은 따로 둔다: `검수 대기 → 추출값 확인 중 → 판정 검수 중 → 저장됨`. 화면이 어느 단계로 이어서 열지 정하는 데 쓴다.
- 재시도: 모델 호출 실패는 지금처럼 호출 단위로 재시도(`run.max_retries`). 작업 전체가 실패하면 자동 재시도 1회, 그래도 실패하면 `failed`로 남겨 사람이 다시 돌린다 (지금의 `/retry`).
- 서버가 다시 켜지면 `running`이던 작업은 `interrupted`로 바꾸고 대기열 앞에 다시 넣는다.

## 5. 2단계 검증
- TO21 검증기 V01~V23(`checks/validator.py`)과 원문 대조(`checks/source_match.py`)를 돌린다. 모델을 부르지 않으므로 대기열 없이 추출 직후 실행한다.
- 결과는 작업 번호에 묶어 저장하고, 3단계가 입력으로 쓴다 (원문 대조에 실패한 칸은 판정 근거로 표시).

## 6. 3단계 2차 평가

### 6.1 원칙 (TO21 정합성검증 개발설계서 v0.4, 7·13·14장)
- **판정은 규칙엔진**이 한다. 상태가 없고, 같은 입력이면 같은 결과다.
- **AI는 설명만** 쓴다. 불일치·경계·근거부족 판정만 판정(finding) + 계산 과정(trace) + 원문 근거(evidence)를 묶어 보낸다.
- 안전장치: 응답의 판정·구분 값은 무시, 설명 속 숫자·코드가 trace·evidence에 모두 있는지 검사, JSON Schema 출력·temperature 0, 실패 시 1회 재요청 후 규칙별 템플릿 문장으로 대체.
- 만든 설명은 저장하고 같은 판정에 대해 다시 만들지 않는다 (설명 문장도 매번 조금씩 다를 수 있어서).

### 6.2 기준 자료를 최신으로 맞춘다
지금 `compliance/` 코드(`single.py`, `sec15.py`, `knowledge.py`, `classifier.py`)는 "설계서 v0.2가 저장소에 없어 팀 결정으로 정했다"고 적혀 있다.
`to21/기업에서받은파일/`에는 이제 다음이 있다:
- `정합성 검증 설계서/정합성검증_설계서_v0.4/` 설계서 v0.4와 규칙표 v0.3 (`규칙표_v0.3/rules`). v0.4는 지식을 엑셀 7종에서 HTODB 16개 테이블로 바꿨다 (59장)
- `규제DB/한컴제공DB/HTODB.zip`과 테이블 설명
- `정합성 검증 테스트/Msds-test_v0.4/ghsclass` (TO21 분류로직 v6 실습 구현, 회귀 테스트 포함)

2차 평가는 이 최신 자료를 기준으로 맞춘다. 지식 제공자는 설계서 v0.4 15장의 3개 함수(`get_reference`, `get_regulation`, `classify_mixture`) 형태를 따르고, 결과 구조는 45장의 consistency 블록을 따른다. 지식 조회는 부록 55~57장(HTODB 테이블·조회 순서·파싱 규칙)을 따른다.

## 7. 4단계 저장

### 7.1 원칙: 덮어쓰지 않고 쌓는다
"판정으로 바로 가기"를 고르면 추출값을 확인하지 않은 채 판정이 먼저 나오고, 판정 검수 중 추출값을 고쳐 다시 판정하는 일이 생긴다.

- **추출 결과는 고치지 않는다.** 사람의 수정은 검수 기록(원래 값·고친 값·근거·검토자·시각)에 따로 쌓는다. 지금 `service/review.py`의 방식을 그대로 쓴다.
- **판정 결과는 버전으로 쌓는다.** 판정 입력 = 추출 결과 + 검수 수정분 + 엔진 버전 + 지식 버전 + 규칙표 버전 + 기준일(as_of). 기준일은 입력이 없으면 업로드한 날(설계서 메시지 명세 ①). "같은 결과"는 같은 기준일·같은 버전끼리의 약속이다. 기준일이 다르면 결과가 달라도 정상이다 (Claude 판단). 입력이 바뀌면 새 버전을 추가하고 이전 버전은 지우지 않는다. 화면은 최신 버전을 보인다.
- **같은 입력이면 다시 계산하지 않는다.** 판정 입력의 해시가 같으면 기존 버전을 쓴다. 같은 작업을 몇 번 다시 돌려도 결과가 늘거나 바뀌지 않는다.
- **판정 검토는 별도 이벤트다.** "불일치 확정·예외 승인·의견"은 판정 결과 안에 쓰지 않고 따로 쌓는다 (설계서 ⑭). 판정 항목 ID(예: 2항 class_code+route_form, 15항 성분×law×item_code)를 버전과 무관하게 고정해서, 새 버전에서도 같은 항목의 이전 검토 이력을 이어서 보인다.

- 검수 기록, 판정 버전, 설명, 판정 검토의 키는 **작업 번호**다. 추출 결과만 파일(sha256)과 추출 설정으로 찾는다.
- **"4. 저장"은 확정본을 남기는 일이다.** 사람이 저장을 누르면 그 순간의 추출 결과·검수 수정분·판정 버전·판정 검토 상태(미검토 포함)를 가리키는 저장본을 하나 만든다. 다시 저장하면 새 저장본이 생기고 이전 것은 남는다. 화면의 "저장됨"과 PDF 출력은 최신 저장본을 쓴다 (Claude 판단).

### 7.2 DB
- **이미 쓰고 있는 PostgreSQL을 쓴다** (결정). `deploy/htodb/compose.yaml`의 PostgreSQL 16, 백엔드는 이미 `psycopg`·`psycopg-pool`을 쓴다 (`compliance/htodb`).
- 같은 서버 안에서 지식DB와 섞지 않는다: 서비스용 스키마(예: `service`)를 따로 두고 쓰기 계정도 따로 만든다. 지식DB(`htodb` 스키마)는 지금처럼 읽기 전용 계정 `kdb_reader`로만 읽는다 (Claude 판단).
- 담는 것: 대기열·작업 상태·사람 구간 상태·추출 결과·검증 결과·검수 기록·판정 버전·설명·판정 검토·저장본. `state.json`·`review.json`은 이 DB로 옮긴다. 원본 PDF와 쪽 이미지는 지금처럼 파일로 둔다.
- 상태를 바꾸는 쓰기(작업 가져가기, 검수 수정 + 새 판정 버전, 저장본 만들기)는 각각 한 트랜잭션으로 한다.
- 추출 결과 표는 TO21 `DB적재_재생성_v0.6.py`의 평탄화 방식을 따라, TO21 재생성 평가가 그대로 돌게 한다. 원래 추출값과 검수 수정분을 얹은 값을 둘 다 재생성할 수 있어야 한다. 화면의 재생성은 지금처럼 수정분을 얹은 값(`review.apply_edits`)을 쓴다.
- DB를 읽는 것은 우리 화면(API 서버)뿐이다.

## 9. 완료 기준
- 4.2 실험을 했고 N과 측정값이 ADR에 있다.
- 20건을 한 번에 넣었을 때 모두 `done` 또는 이유가 남은 `failed`로 끝나고, 걸린 시간이 기록된다.
- 처리 중 서버를 껐다 켜도 작업이 이어진다.
- 같은 문서를 두 번 넣으면 (재사용 끔, 같은 기준일) 판정이 같다 (설명 제외). 설계서 v0.4 49장의 "같은 입력 2회 실행" 테스트.
- 판정 검수 중 추출값을 고치면 새 판정 버전이 생기고, 이전 버전과 판정 검토 이력이 남는다.
- 두 경로(추출값 확인부터 / 판정 바로 가기) 모두 판정과 저장까지 갈 수 있고, 미검토가 남아도 저장된다.
- 서로 다른 작업자 프로세스 2개를 띄워도 한 작업이 두 번 처리되지 않는다.
- AI 설명의 숫자 환각 0건 (검사에 걸린 건은 템플릿 문장으로 대체됨).
