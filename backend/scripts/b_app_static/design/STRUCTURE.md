# 최근 결과에서 문제의 원문을 확인하고, 같은 대상을 다시 시험하는 구조로 바꿉니다.

관문 ② 구조안입니다. 사용자가 2026-10-31에 승인했습니다. 함께 정한 것은 8절에 있습니다.
화면 배치만 보는 흑백 설계도는 [wireframes.html](wireframes.html)입니다.
화면 이름과 번호는 두 파일에서 같습니다.
모든 예시 점수와 문서 내용은 가짜입니다. 실제 실행 성공을 뜻하지 않습니다.

대상은 프로젝트를 처음 보는 개발 입문자와 매일 시험하는 B입니다.
사용 목적은 작업 완료(Operate)입니다. A와 C는 저장된 결과를 서버 없이 확인합니다.
기준 폭은 1440px입니다. 1280~1680px에서는 열 너비를 조절합니다.
시각 스타일 선택은 관문 ③에서 합니다. 이번에는 제품 코드와 기존 문서를 고치지 않습니다.
첫 사용 안내의 세부 단계와 문구는 Claude가 `first-use-guide`로 작성했습니다. ‘첫 사용 안내 (두 갈래)’ 절에 있습니다.

근거는 지정한 맥락 문서를 먼저 읽고 확인했습니다.

- 승인된 진단: [CRITIQUE.md](../CRITIQUE.md)의 문제 24개와 과제 12개.
- 결정: [재설계 계획](../../../docs/plan/B_앱_재설계_계획_20261030.md), [승인 기록](../../../docs/plan/B_앱_재설계_승인.md), [ADR-028](../../../docs/ADR.md), [PRD 13번](../../../docs/PRD.md), [UI 지침](../../../docs/UI_GUIDE.md).
- 계약: [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md)의 작업 화면 API 표와 `phases/app-redo-api/step0~7.md`.
- 현행 증거: 지정한 데스크톱 캡처 11장과 `app.js` 1~2074행. `index.html`, `guide.html`, `b_app_text.py`도 대조했습니다.
- 적용 지침: impeccable의 `shape`, `onboard`, `mode-operate`. 맥락 실행기는 성공했습니다. 기존 PRODUCT·DESIGN의 ‘다듬기’ 지침은 현행 증거로만 사용했습니다.

## 1. 사용자가 이 앱으로 끝내려는 일 5가지

1. 최근 결과의 점수와 총점 손실이 가장 큰 문제를 이해한다.
2. 문제의 값을 원문 줄과 맞춰 보고 차이의 이유를 확인한다.
3. 같은 문서의 같은 항을 다시 시험하고 결과 변화를 확인한다.
4. 문서를 묶어 실행하고 여러 실행의 차이를 비교한다.
5. 필요한 모델을 연결하고 사용한 서버의 시간과 비용을 관리한다.

왼쪽 메뉴는 두 묶음입니다. 작업 순서는 위에서 아래로 최근 결과 → 원문 대조 → 시험하기 → 실행 비교입니다. 그 밖의 화면은 모델 연결, 작업 기록, 도움말입니다.
앱의 목적과 문서 정의는 왼쪽 메뉴 아래에 둡니다.
선택한 메뉴와 현재 하위 화면을 글로 표시합니다.
옛 주소 `#s09`는 S03으로 이어지므로 시험하기 메뉴가 선택 상태입니다. S10에서는 실행 비교 메뉴를 선택 상태로 둡니다.
도움말을 열 때는 출발 화면과 선택 대상을 기억합니다.

막대의 세 값은 다음 뜻입니다. 한 줄에는 현재 선택과 상태와 비용을 둡니다. 원래 폴더, 조회 시각, 정답 신뢰 범위는 말풍선과 P01에 남깁니다. 현재 기준과 실행 당시 기준은 계속 구분합니다.

| 칸 | 항상 보이는 정보 | 바꾸는 곳 | 바뀌는 정보 | 바뀌지 않는 정보 |
|---|---|---|---|---|
| 문서 묶음 | 쉬운 이름, 채점할 수 있는 문서 수 | P01 | 문서 목록, 실행 후보, 시험 가능 여부, 원문과 쪽 그림. 선택한 묶음의 최근 결과를 찾음 | 저장된 실행 결과와 실행 당시 입력. 이미 시작한 작업 |
| 정답지 | 정답 이름. 초안(실버)과 검수 답안(골드)의 뜻은 말풍선과 P01 | P01 | 총점, 필수 달성 수, 23개 점수, 문제 순서, 비교, 이력, 행 수 대조, 원문의 정답 열, 정답지 주의 | 추출 결과, 원문, 과거 작업의 원래 점수 기록 |

예시 표기: `문서 묶음: 이전 개발 자료 (prev/version9)`는 현재 계약의 식별자를 사용합니다.
정답지를 바꾸면 새 모델 호출 없이 저장된 결과를 다시 채점합니다.
문서 묶음만 바꾸는 일은 기존 결과를 새 원문으로 다시 추출하는 일이 아닙니다.

조회 중인 실행과 다음 시험의 조건을 구분합니다.

1. S01의 점수에는 ‘이 실행이 사용한 묶음’을 붙입니다.
2. 다른 묶음의 실행을 직접 고르면 전역 선택과의 차이를 표시합니다.
3. S02에서 과거 결과의 근거를 열 때는 그 실행이 사용한 원문을 기본으로 엽니다.
4. 전역 묶음이 다르면 ‘원문: 실행 당시 묶음 / 다음 시험: 선택 묶음’을 모두 보입니다.
5. 다른 묶음으로 원문을 바꾸면 근거 선택을 다시 확인합니다. 같은 줄 번호라고 같은 근거로 취급하지 않습니다.
6. S03으로 보낼 때 조건 차이를 검토합니다. 예전 원문으로 재시험할지 현재 묶음을 쓸지 명시적으로 고릅니다.

P01에서 적용하기 전에는 현재 화면을 바꾸지 않습니다.
적용 후에는 영향을 받는 영역을 ‘다시 계산 중’으로 바꿉니다.
이전 응답이 늦게 와도 새 선택의 값으로 표시하지 않습니다.
새 조회 실패 시에는 실패한 기준을 표시합니다. 이전 점수를 새 기준 아래 섞어 놓지 않습니다.
새 묶음에 고른 문서가 없으면 빈 선택과 이유를 남깁니다. 첫 문서로 몰래 바꾸지 않습니다.
유효한 문서·항·기준 실행은 유지합니다. 무효가 된 쪽·값·근거 줄만 해제합니다.
편집 중 지시문은 메모리에 유지합니다. 출처가 다른 경우 전송 전에 재확인을 요구합니다.
이미 시작한 작업은 시작 당시 조건을 계속 표시합니다.

키보드로 메뉴와 모든 행동에 도달할 수 있어야 합니다.
확인창은 취소 후 원래 단추로 포커스를 돌려줍니다.
표와 긴 경로는 줄바꿈합니다. 호출 격자의 16항은 1280px에서도 가로 스크롤 없이 배치합니다.
색 대신 상태 글과 테두리로도 선택과 오류를 구분합니다.

## 5. 핵심 흐름 다섯 개

### 흐름 1. 첫 사용 갈래 1 — 점수에서 문제의 원문 줄까지

1. S01 안내 띠 또는 상단 ‘처음 사용’에서 S08을 엽니다.
2. ‘서버 없이 결과 읽기’를 고릅니다.
3. S01에서 최근 유효한 저장 결과의 점수와 두 목표를 봅니다.
4. 총점 손실이 가장 큰 항목의 ‘문제의 원문 보기’를 누릅니다.
5. S02가 같은 실행과 문서와 항목을 엽니다.
6. 문제 값을 고릅니다. 실제로 존재하는 원문 줄의 선택 표시를 확인합니다.
7. 이때만 갈래 1 성공을 기록합니다. 원문 로딩이나 줄 대응에 실패하면 현재 단계를 유지합니다.

첫 줄을 임의로 여는 것으로 성공을 만들지 않습니다.
가장 큰 항목의 상세 근거가 없으면 ‘근거를 아직 연결하지 못함’을 표시합니다.
실행이 전혀 없으면 성공 경로를 시작할 수 없다고 알립니다. S03 입력 확인 연습으로 갈 수 있습니다.
세부 안내 문구와 단계별 실패 복구는 ‘첫 사용 안내 (두 갈래)’의 갈래 1을 따릅니다.

### 흐름 2. 첫 사용 갈래 2 — 한 항 실제 시험

1. S08의 두 번째 갈래와 S03의 안내 띠에 진입점을 둡니다.
2. S03에 개발용 문서 하나와 항 하나를 고르는 안내 자리를 둡니다.
3. 모델이 없으면 S06으로 이동하는 자리를 둡니다. ‘입력 확인 연습’도 별도로 둡니다.
4. S03에 실제 작업 진행과 결과 확인 자리를 둡니다.
5. 실제 시험 작업이 성공하고 사용자가 결과를 열었을 때만 갈래 2를 완료합니다.

연습은 ‘연습 완료’로만 기록합니다. 실제 성공 이력에 합치지 않습니다.
건너뛰기와 다시 보기는 S08에서 제공합니다. 기존 성공 기록을 초기화하지 않습니다.
세부 단계·성공 증거·실패 복구·건너뛰기 문구는 ‘첫 사용 안내 (두 갈래)’의 갈래 2를 따릅니다.

### 흐름 3. 문서 묶음과 정답지 바꾸기

1. 어느 화면에서든 전역 문서 또는 정답지 칸을 누릅니다.
2. P01에서 현재값과 후보를 나란히 봅니다.
3. 문서 수와 정답 있는 수를 확인합니다. 쓸 수 없는 후보에는 이유를 보입니다.
4. 평가용 10건은 잠긴 이유만 표시합니다. 내용과 그림은 요청하지 않습니다.
5. ‘적용’을 누르면 전역 기준을 함께 바꿉니다. 관련 결과를 다시 읽습니다.
6. 대상이 여전히 유효하면 유지합니다. 새 묶음에 없으면 새 대상을 고르게 합니다.
7. 새 정답지로 계산한 점수의 출처와 채점 문서 수를 확인합니다.

정답지가 일부 문서에만 있으면 그 문서만 채점했다는 범위를 점수 옆에 둡니다.
예시 구성은 가짜입니다: 문서 10건 중 정답 있는 3건을 ‘3/10건 채점’으로 표시합니다.
평가 문서의 직접 요청이 404여도 오류를 평가 잠금이라고 추측하지 않습니다.
잠금 사유는 문서 목록의 계약 정보로 확인한 경우에만 표시합니다.

### 흐름 4. 한 항 시험 — 문제 → 원문 → 다시 시험

1. S01에서 문제를 고릅니다. 실행·문서·채점 항목을 기억합니다.
2. S02에서 해당 항을 열고 결과 값과 원문 줄을 맞춥니다.
3. ‘이 문서의 이 항 시험하기’를 누릅니다.
4. S03에 같은 문서와 항을 채웁니다. 기준 실행과 실제 입력 묶음을 함께 보입니다.
5. 다른 모델을 고르거나 지시문을 수정하면 바뀐 조건을 표시합니다.
6. 준비 조건을 확인한 뒤 실제 시험을 보냅니다. 실행 가능 여부는 서버 응답을 따릅니다.
7. 결과 요약에서 해당 항을 교체해 다시 계산한 전후 점수를 봅니다.
8. 새 결과와 원래 기준 실행을 구분합니다. ‘원문으로 돌아가기’로 같은 문서·항·값 위치를 복원합니다.
9. 값이 새 결과에 없으면 해당 항까지 돌아갑니다. ‘이 값은 새 결과에 없음’을 표시합니다.

보존 대상은 실행·묶음·정답지·문서·항·값 경로·쪽·줄·스크롤 위치입니다.
서버 연결을 다녀와도 문서와 항을 유지합니다. 연결 조회가 입력을 덮어쓰지 않습니다.
새 시험의 값을 저장된 기준 실행의 값인 것처럼 덮어 보여 주지 않습니다.
문서 목록 밖 자료의 실행 가능성은 문서별 `runnable.try`와 `runnable.run`을 따릅니다.
불가 사유는 `run_reason`을 씁니다. 신규 40건이라는 이름만으로 시험을 허용하지 않습니다.

### 흐름 5. 모델 연결 — 기존 자원 확인부터 시험 복귀까지

**RunPod: 시간당 비용이 드는 임대 모델 서버입니다. 서버 한 대를 Pod라고 부릅니다.**

1. S06은 지금 상태의 단계로 열립니다. 켜진 AI가 없으면 ① 서버 고르기, 만드는 중이면 ③ 준비 기다리기, 고른 AI가 응답하면 ④ 쓰고 나서 끄기입니다.
2. 앱이 이어받은 Pod가 있으면 ④에서 숫자를 보이고, 번호와 ‘기존 서버 이어 쓰는 중’은 자세히 서랍에 보입니다.
3. 모델 응답과 기대 모델이 일치하면 행동 줄의 다음 행동이 ‘시험으로 돌아가기’입니다.
4. 설정 문제가 있으면 단계 안에 사실과 할 일, ‘설정 다시 읽기’를 보입니다. 필요한 설정 이름은 자세히 서랍에 있습니다.
5. ①에서 두 서버를 나란히 비교합니다. 고른 AI를 켤 수 있는 서버를 먼저 보이고 표시를 붙입니다.
6. ②에서 ‘새 서버 요금 확인하기’를 누르면 P02가 열립니다. 시간당 비용과 대상 모델을 확인합니다. 기존 Pod가 있으면 중복 생성 가능성도 보입니다.
7. 생성 후 ③은 앱이 확인한 상태(서버, AI 응답)까지만 보입니다. 가짜 진행률을 만들지 않습니다.
8. 실제 모델 응답이 준비되면 ④로 넘어가고 고른 시험으로 돌아갈 수 있습니다.
9. 사용 후 앱 소유 Pod만 삭제할 수 있습니다. P02에서 대상을 다시 확인합니다.

현재 상세 계약은 최신 앱 소유 Pod를 자동으로 이어받습니다.
임의 Pod를 선택해 이어받는 새 API나 단추를 가정하지 않습니다.
여러 개가 발견되면 자동 선택된 번호와 나머지 번호를 구분합니다.
비용을 읽지 못하면 무료로 표시하지 않습니다. 자동 삭제도 확인된 상태만 보여 줍니다.

**RNGD: 사내 모델 장비입니다. 연결 통로(SSH 터널)와 모델 준비는 별개입니다.**

1. 터널과 모델을 두 줄 상태로 확인합니다.
2. 터널이 닫혀 있으면 ‘터널 열기’의 요약을 확인하고 실행합니다.
3. 터널이 열리면 사용할 모델을 고릅니다.
4. 다른 모델이 떠 있으면 먼저 내리는 확인을 거칩니다. 동시에 한 모델만 사용합니다.
5. ‘모델 올리기’에서 필요한 카드와 예상 15~25분 대기를 확인합니다.
6. 올리는 중에는 경과시간과 마지막 확인 시각을 보입니다. 완료율은 만들지 않습니다.
7. 다른 화면으로 이동해도 전역 모델 칸에서 상태를 볼 수 있습니다.
8. 기대 모델의 응답이 확인되면 ‘준비됨’을 보입니다. 보존된 시험으로 돌아갑니다.

진행 중 작업이 있을 때 터널을 닫거나 모델을 교체하지 못하게 합니다.
터널 열기는 진행 중에도 허용한다는 계약을 따릅니다.
진단 값이 없거나 최신 조회가 실패하면 ‘상태 확인 안 됨’을 씁니다. 준비됨으로 추정하지 않습니다.

| 갈래 | 첫 실제 결과 | 성공 사건 | 확인 근거 | 대체 체험 |
|---|---|---|---|---|
| 갈래 1 · 서버 필요 없음 | 최근 실행의 가장 큰 문제 값이 원문 어느 줄에서 왔는지 본다 | S02에서 그 문제의 ‘다름’ 값과 근거 줄이 함께 선택되어 보임 | `/api/doc`의 `values[]`·`lines[]`, 화면의 줄 선택 표시 | 없음. 저장된 실행이 없으면 시작하지 않음 |

1. 버튼을 누른 사실은 성공이 아닙니다. API 값과 화면 사건이 함께 있을 때만 성공을 기록합니다.
2. ‘다음’ 버튼은 앞 단계의 증거가 있을 때만 켭니다. 버튼 활성화와 첫 성공 기록은 따로 판정합니다.

4. 상태를 모르면 ‘확인 안 됨’이라고 씁니다. ‘없음’이나 ‘꺼짐’으로 단정하지 않습니다.
5. 두 갈래는 서로 독립입니다. 갈래 1을 먼저 권합니다. 갈래 2만 해도 됩니다.
6. 화면을 다시 열어도 시험을 자동으로 다시 보내지 않습니다. 화면을 자동으로 옮기지도 않습니다.

#### 1-3. 문제 값의 원문 줄 확인 · S02 — 갈래 1 첫 성공

- **사용자 행동**: 오른쪽에서 ‘다름’ 표시가 붙은 값을 하나 고릅니다(누르기 또는 Enter). 왼쪽에 그 값의 근거 줄이 선택된 것을 봅니다. 왼쪽 줄을 먼저 골라도 됩니다.
- **성공 증거**: 아래가 모두 참일 때만 기록합니다.
  1. 고른 값 `v`가 `/api/doc`의 `values[]`에 있고 `v.section`이 목표 항입니다.

### 갈래 2 — 한 문서의 한 항 시험하기

준비 조건은 기능 준비 상태에서 읽습니다.

- 문서: `/api/options`의 `sets[]` 중 전역 묶음의 `docs[]`에 `runnable.try`가 참인 문서가 있습니다.
- 모델: 고른 모델의 `models[].connected`가 참입니다. 연습에는 필요 없습니다.
- 정답지: 시험 전후 점수에만 씁니다. 성공 조건이 아닙니다.

#### 2-1. 시험 대상 고르기 · S03

  - 항을 둘 이상 고름: [다음]을 끄고 문구를 보입니다. 안내 밖 S03에서는 여러 항이 그대로 됩니다.

  - `status` = `unknown`: 앱이 다시 켜져 끝을 모른다고 씁니다. [작업 기록 보기]를 둡니다.

- **표시 규칙**
  - 이름은 ‘입력 확인 연습’입니다. 처음 한 번은 ‘입력 확인 연습(dry-run)’으로 씁니다.
  - S03 머리 표는 ‘연습 완료’입니다. S05 종류 칸은 ‘연습’입니다. S08 표는 ‘연습’ 열에만 씁니다.
  - ‘성공’이라는 말을 연습에 단독으로 쓰지 않습니다.
  - `first_success_recorded` 사건을 내지 않습니다. `practice_recorded`만 냅니다.
  - `dry_run` 키가 없는 작업은 실제 성공으로 세지 않습니다. step 7 구현 전 백엔드에서는 갈래 2를 완료할 수 없습니다.
- **화면 문구 초안**
  - 시작 전: "입력 확인 연습(dry-run)은 모델을 부르지 않습니다." "보낼 입력과 모델 지시문(프롬프트)만 만듭니다." "연습은 성공 기록에 넣지 않습니다."
  - 완료: "입력과 지시문만 확인했습니다." "실제 시험 성공은 아직 없습니다." "할 일: 모델을 연결하고 실제 시험을 보내세요."
  - 완료 뒤 행동: [모델 연결하기] [시험 대상으로 돌아가기]
  - ③~⑥ 자리: "연습에서는 모델 응답과 전후 점수를 만들지 않습니다."

### 세 가지 기록

세 기록은 서로를 근거로 삼지 않습니다. 진행 상태로 준비 상태를 추정하지 않습니다. 준비 상태로 성공을 추정하지 않습니다.

| 기록 | 답하는 질문 | 저장 | 쓰는 때 | 지우는 때 |
|---|---|---|---|---|
| 안내 진행 상태 | 안내의 어느 단계까지 확정했는가 | `runs/manual/journey.json`의 `progress` | 단계 증거 확보, 건너뛰기, 닫기, 다시 보기, 이어하기 | 다시 보기가 갈래 상태를 처음으로 돌림 |

- 갈래 1 성공은 S01 ‘가장 큰 문제’ 카드에서 S02로 온 경우만 셉니다.
- 갈래 2 성공은 작업 화면이 띄운 작업(`/api/jobs`에 있는 작업)만 셉니다. 같은 작업을 다시 열어도 다시 세지 않습니다(`last_job`과 같으면 건너뜀). 다른 터미널의 작업(`running[].mine` 거짓)은 세지 않습니다.

**기능 준비 상태 (메모리)**

- 다시 확인하는 때: 갈래 시작, 단계 진입, S06에서 돌아옴, 창이 다시 보임(`visibilitychange`), P01 적용, `POST /api/servers/reload_env` 뒤.
- 요청마다 순번을 붙입니다. 더 늦게 보낸 요청의 응답이 이미 있으면 앞선 응답을 버립니다.
- ‘마지막 확인’ 시각은 브라우저가 응답을 받은 시각입니다. 서버 쪽 확인 시각 필드는 없습니다(O7).
- 갈래 진행 중 P01에서 정답지를 바꾸면 갈래 1은 1-1부터 다시 읽습니다. 이미 남긴 성공 기록은 그대로입니다.
- 갈래 진행 중 문서 묶음을 바꾸면 갈래 2는 고른 문서의 `runnable.try`를 다시 봅니다. 거짓이면 2-1로 돌아갑니다. 이미 보낸 작업은 시작 당시 조건을 유지합니다.

### 저장 형태 — journey v2

§8 질문 2의 결정에 따라 첫 사용 기록은 브라우저가 아니라 프로젝트에 둡니다. 브라우저 `localStorage`는 저장소로 쓰지 않습니다.
저장 API는 보충 백엔드 phase가 시험을 먼저 쓰고 만듭니다(O9). 아래는 그 phase가 따를 계약입니다.

- 파일은 저장소 맨 위 기준 `runs/manual/journey.json`입니다. 체크아웃 하나에 기록 하나입니다.
- 앱은 127.0.0.1에만 열립니다. 그래서 사용자 구분이 없습니다.
- 이 파일은 로컬에서 git에 올리지 않습니다(`runs/manual/jobs/`와 같은 방식).
- 지금 `.git/info/exclude`에는 `/runs/manual/jobs/`만 있습니다. 보충 phase가 `/runs/manual/journey.json` 줄을 더해야 합니다.

| 길 | 요청 본문 | 응답 | 규칙 |
|---|---|---|---|
| `GET /api/journey` | 없음 | `{"journey": <v2>, "problems": [...]}` | 파일이 없으면 기본 v2(모두 `null`·`not_started`). 깨진 부분만 기본값으로 돌리고 `problems`에 적음. 나머지 부분은 유지 |
| `PUT /api/journey` | `{"journey": <v2>}` | 합친 v2 journey | 형과 아는 키만 받음. 본문 16 KB 이하. `outcomes`는 줄지 않게 병합. `progress`·`pending`은 교체. 임시 파일에 쓴 뒤 이름 바꾸기로 한 번에 씀. 잘못된 본문은 400과 한국어 문장 |

- `outcomes` 병합: `real`·`practice`를 지우지 않습니다. `count`를 낮추지 않습니다. `first_at`은 이른 값, `last_at`은 늦은 값을 둡니다.
- `last_job`은 `last_at`이 늦은 쪽의 값을 둡니다(제안).
- 그래서 ‘다시 보기는 성공 기록을 지우지 않는다’는 규칙을 서버가 지킵니다. 화면 코드가 `outcomes`를 비워 보내도 기록은 남습니다.
- `problems` 항목 모양 제안: `{"part": "progress" | "outcomes" | "pending" | "file", "message": 한국어 한 문장}`. 확정은 보충 phase가 합니다.
- `migrated_from`은 한 번 `1`이 되면 유지합니다(제안).

```json
{
  "version": 2,
  "progress": {
    "active": "t2",
    "dismissed_at": null,
    "t1": {"state": "completed", "step": 3, "updated_at": "2026-10-31T00:58:00.000Z"},
    "t2": {"state": "in_progress", "step": 1, "updated_at": "2026-10-31T01:02:00.000Z"}
  },
  "outcomes": {
    "t1": {"real": {"first_at": "2026-10-31T00:58:00.000Z", "last_at": "2026-10-31T00:58:00.000Z", "count": 1}},
    "t2": {
      "real": null,
      "practice": {"first_at": "2026-10-31T00:55:00.000Z", "last_at": "2026-10-31T00:55:00.000Z", "count": 1,
                   "last_job": "20261031_095500_try_a1b2c3"}
    }
  },
  "pending": null,
  "migrated_from": null
}
```

| 필드 | 값 | 뜻 |
|---|---|---|
| `version` | `2` | 형식 번호 |
| `progress.active` | `"t1"` `"t2"` `null` | 지금 안내 중인 갈래 |
| `progress.dismissed_at` | 시각 또는 `null` | 안내를 닫은 시각. 있으면 안내 띠를 띄우지 않음 |
| `progress.t1`·`t2`.`state` | `not_started` `in_progress` `skipped` `completed` | 갈래 상태 |
| `progress.t1`·`t2`.`step` | 갈래 1은 0~3, 갈래 2는 0~4 | 마지막으로 확정한 단계. 0은 시작 전 |
| `progress.t1`·`t2`.`updated_at` | 시각 또는 `null` | 마지막으로 바뀐 시각 |
| `outcomes.t1.real` | `{first_at, last_at, count}` 또는 `null` | 갈래 1 실제 성공 |
| `outcomes.t2.real` | `{first_at, last_at, count, last_job}` 또는 `null` | 실제 시험 성공 |
| `outcomes.t2.practice` | `{first_at, last_at, count, last_job}` 또는 `null` | 연습 완료 |
| `pending` | `{attempt, job, mode, started_at}` 또는 `null` | 안내에서 보내고 아직 판정하지 않은 시도 하나. `mode`는 `real` 또는 `practice` |
| `migrated_from` | `1` 또는 `null` | v1에서 옮겼는지 |

- 시각은 `Date.prototype.toISOString()` 형식입니다. 화면에는 내 컴퓨터 시각으로 보입니다.
- 저장하지 않는 것: 문서 번호, 실행 이름, 항 번호, 값, 지시문, 묶음·정답지 id, 모델 태그·주소, 경로, 키.
- 작업 번호(`last_job`, `pending.job`)만 예외입니다. 시작 시각과 작업 종류만 담긴 번호이고 결과 다시 열기에 씁니다.
**화면 쪽 동작**

- 켤 때 `GET /api/journey`로 읽습니다. 응답을 받기 전에는 안내 띠와 재방문 알림을 띄우지 않습니다.
- `problems`가 있으면 한 번 알립니다.
  - 문구: "안내 기록 일부를 읽지 못해 처음 상태로 돌렸습니다." "{problems[].message}"
- 상태가 바뀌면 메모리를 먼저 바꾸고 journey 전체를 `PUT`합니다. 응답으로 받은 합친 journey로 메모리를 바꿉니다.
- `PUT`은 한 번에 하나만 보냅니다. 보내는 중에 또 바뀌면 끝난 뒤 최신 상태 하나만 보냅니다. 앞선 요청의 늦은 응답은 버립니다.
- 실패(`GET`·`PUT`의 연결 실패나 4xx·5xx): 이 탭의 메모리 상태로 계속합니다. 제품 기능은 그대로 됩니다. 알림은 한 번만 보입니다. 다음 상태 변화 때 다시 `PUT`합니다.
  - 문구: "기록을 저장하지 못했습니다." "작업 화면 서버가 켜져 있는지 확인하세요." "다음 단계로 넘어갈 때 다시 저장합니다."
  - 400이면 둘째 문장 대신 응답의 한국어 문장을 보입니다.
- 두 탭: `progress`는 마지막 `PUT`이 이깁니다. `outcomes`는 서버 병합 때문에 잃지 않습니다. 창이 다시 보이면(`visibilitychange`) `GET`으로 다시 읽어 그립니다.
- v1에서 옮기기: `GET` 결과의 `migrated_from`이 `null`이면 localStorage의 v1 `b_app.journey`를 `try/catch`로 읽습니다.
  - v1(`version: 1`)이 현행 검사(`loadJourney`)를 통과하면 아래 표대로 바꿔 `migrated_from: 1`로 한 번 `PUT`합니다.
  - 서버 `progress`가 기본값이 아니면 서버 `progress`를 유지합니다. v1에서는 `outcomes`만 더합니다.
  - v1 키는 지우지 않습니다. v1이 없거나 검사를 통과하지 못하면 옮기지 않습니다.
- 브라우저에 남는 다른 값(`b_app.cards`, `b_app_pick` 등 화면 편의 값)은 이 결정과 무관합니다.

| v1 값 | v2 값 |
|---|---|
| `completed` 참, `first_success_at` = T | `outcomes.t1.real` = `{first_at: T, last_at: T, count: 1}`, `progress.t1` = `completed`·`step 3` |
| `last_step` 1~2, 미완료 | `progress.t1` = `in_progress`·`step` = `last_step` |
| `dismissed` 참 | `progress.dismissed_at` = 옮긴 시각 |
| 그 밖 | 기본값 |

v1의 완료 조건(가장 큰 문제 항에서 정답과 다른 값의 근거 줄 선택)은 갈래 1 성공 조건과 같습니다. 그래서 실제 성공으로 옮깁니다.

### 다시 보기·건너뛰기·닫기·이어하기

| 행동 | 바뀌는 것 | 그대로인 것 | 문구 초안 |
|---|---|---|---|
| 갈래 건너뛰기 | 그 갈래 `state` = `skipped`, `step` 유지, `active` = null | `outcomes`, 제품 자료, 보낸 작업 | "이 갈래를 건너뛰었습니다." "처음 사용 안내에서 언제든 다시 시작할 수 있습니다." |
| 안내 닫기 | `dismissed_at` 기록, `active` = null | 갈래 상태, `outcomes` | "안내를 닫았습니다." "위쪽 ‘처음 사용’에서 다시 열 수 있습니다." |
| 다시 보기 | 두 갈래 `not_started`·`step 0`, `active`·`dismissed_at` = null, `pending` = null | `outcomes` 전부, 보낸 작업, 브라우저의 화면 편의 값(`b_app.cards` 등) | 버튼 아래: "진행 단계만 처음으로 돌립니다." "성공 기록과 연습 기록은 그대로 둡니다." |
| 이어하기 | `active` = 그 갈래 | 나머지 | "갈래 2를 2단계부터 이어갑니다." |

- 다시 보기에는 확인창이 없습니다. 지우는 기록이 없기 때문입니다.
- 다시 보기는 `progress`·`pending`만 바꾼 journey를 `PUT`합니다. 서버가 `outcomes`를 병합하므로 성공 기록은 줄지 않습니다.
- 다시 보기 때 진행 중인 시험은 멈추지 않습니다. 안내에서 떼어 냅니다. 문구: "진행 중인 시험은 멈추지 않습니다." "결과는 작업 기록에서 볼 수 있습니다."
- 이어하기는 저장된 `step`의 다음 단계로 갑니다. 그 단계에 필요한 입력(목표 문제, 고른 문서와 항)이 메모리에 없으면 그 입력을 만드는 가장 이른 단계로 갑니다. 이유를 한 문장으로 알립니다.
  - 예: "새로 열어 고른 문서와 항이 사라졌습니다." "시험 대상을 다시 고르세요."
- 갈래가 `completed`이면 [다시 하기]를 보입니다. 다시 해도 `outcomes`는 더해지기만 합니다.

### 취소와 늦은 응답

1. 시도마다 브라우저가 임의 번호(`attempt`)를 만듭니다. 요청과 응답 처리는 이 번호를 들고 다닙니다.
2. 응답이 왔을 때 현재 시도 번호와 다르거나 그 시도가 취소 상태면 버립니다. `late_response_discarded` 사건을 남깁니다.
3. [시험 멈추기]는 `POST /api/jobs/<id>/stop`을 부릅니다. `stopped`가 참이면 시도는 취소입니다. 이후 `status`나 `/result`가 와도 성공으로 기록하지 않습니다.
4. `stopped`가 거짓이고 작업이 `done`이면 취소가 아닙니다. "멈추기 전에 시험이 끝났습니다."를 보이고 보통처럼 판정합니다.
5. 작업 번호를 받기 전에 취소하면 늦게 온 POST 응답을 시도에 붙이지 않습니다. 작업은 이미 시작됐을 수 있습니다.
   - 문구: "취소 전에 보낸 시험이 작업 기록에 남았습니다." [작업 기록 보기] [멈추기]
6. 떼어 내기: 시험 중에 대상(문서·항·모델·묶음·정답지)을 바꾸거나 갈래를 건너뛰거나 다시 보기를 누르면 시도를 안내에서 떼어 냅니다. 작업은 멈추지 않습니다. 떼어 낸 작업은 안내 단계를 올리지 않습니다.
7. 떼어 낸 작업도 실제 시험이 성공하고 사용자가 결과를 열면 `outcomes.t2.real`에는 기록합니다. 취소한 작업은 어느 기록에도 성공으로 넣지 않습니다.
8. 새로고침 뒤 `pending.job`이 있으면 `/api/jobs`에서 찾습니다. 진행 중이면 알림을 보이고, 끝났으면 2-4로 판정합니다. 목록에 없으면 `pending`을 비우고 "지난번 시험 기록을 찾지 못했습니다."를 보입니다.
9. 새로고침 뒤 `pending.job`이 null이면 보냈는지 알 수 없습니다. `pending`을 비우고 "보냈는지 확인하지 못했습니다." "작업 기록을 확인하세요."를 보입니다.

### 확인할 장면 (미실행)

설계만 했으므로 아래는 모두 실행하지 않았습니다. 구현 뒤 화면 시험으로 확인합니다.

1. 첫 방문: 안내 띠가 S01에만 보이고, 닫으면 다시 열어도 보이지 않습니다.
2. 1-2에서 새로고침: 갈래 1이 2단계 알림으로 돌아오고 목표 문제를 다시 계산합니다.
3. 2-3 진행 중 새로고침: `pending.job`으로 상태를 다시 읽고 자동으로 다시 보내지 않습니다.
4. 두 갈래 완료 뒤 재방문: S01 최근 결과 요약으로 열리고 안내 띠와 알림이 없습니다.
5. 다시 보기: 진행은 처음으로 돌아가고 S08 안내 기록 표의 성공·연습 시각과 횟수는 같습니다.
6. 기록 API 실패(`GET`·`PUT /api/journey`가 500이나 연결 실패): 안내와 시험이 그대로 되고 저장 실패 문구가 한 번 보입니다. 다음 상태 변화 때 다시 `PUT`합니다.
7. 기록 파일 일부 손상: `progress`만 깨뜨리면 `GET`의 `problems`에 그 부분이 나오고 `outcomes`는 남습니다.
8. `outcomes`를 비우거나 `count`를 낮춘 `PUT`: 응답의 `outcomes`가 줄지 않습니다.
9. 두 탭: 한 탭이 연습을, 다른 탭이 실제 성공을 기록해도 둘 다 남습니다.
10. v1 기록만 있는 브라우저: 한 번 옮겨지고 `migrated_from`이 `1`이 됩니다. v1 키는 남습니다.
11. 연습만 하고 모델 없음: S08 갈래 2가 ‘연습 1회 · 실제 성공 아직 없음’이고 `first_success_recorded`가 없습니다.
12. 멈추기 뒤 늦게 온 `done`·`/result`: 성공 기록이 생기지 않습니다.
13. 안내 대상이 없는 화면(대상 식별자 제거): 막대가 멈춤 문구를 보이고 다른 자리를 가리키지 않습니다.
14. 키보드만으로 두 갈래를 끝까지 진행합니다. 포커스는 안내 버튼으로 옮긴 화면의 대상으로 갑니다.
15. 1280px 폭에서 막대 글과 버튼이 잘리지 않습니다.

| G04 | 문제에서 특정 근거 값으로 연결하는 식별자 | 현재 `openScoreSource`는 상세의 첫 문서와 항까지만 연결함. 실제 문제 값과의 대응은 보장되지 않음 | 문제별 문서·항·값 경로 또는 근거 줄의 대응 여부. 없으면 해당 항을 열고 사용자가 값을 선택. 다른 값을 자동 성공 증거로 쓰지 않음 |
| G05 | 과거 작업의 실행 조건과 재채점 조건 구분 | 작업 POST는 set·key를 받음. 작업 목록 표는 원래 조건의 보존 필드를 명시하지 않음 | 작업 상세/결과에 실제 set·key·모델·문서·항·기준 실행과 실제 호출 여부. 완료 시 고른 정답지 내용 판별값. 없으면 ‘기록 당시 기준 미확인’ 표시 |

다음은 새 계약이 필요하지 않습니다.

- 문서별 실행 허용은 `/api/options`의 `runnable`과 `run_reason`을 그대로 씁니다.
- 평가 잠금의 이유는 `/api/sets` 목록을 씁니다. 직접 원문 요청의 404를 바꾸지 않습니다.
- Pod 이어 쓰기는 기존 자동 인계와 `session.adopted`를 씁니다.
- 모델 준비 시간은 `loading_since`를 씁니다. 작업 완료율 API를 추가하지 않습니다.
- 선택과 복귀 위치는 현재 브라우저 메모리에서 유지합니다.
- 갈래별 성공 기록은 프로젝트 파일 `runs/manual/journey.json`에 최소 메타데이터만 저장합니다(8절 질문 2 결정). 전문과 비밀값은 저장하지 않습니다. 저장 API(`GET`·`PUT /api/journey`)는 보충 백엔드 phase가 만듭니다.

## 8. 사용자가 정할 것 — 열린 질문 3개

사용자가 2026-10-31에 관문 ②를 승인하며 아래처럼 정했습니다.

- 질문 1: 해당 묶음의 결과 없음 표시(추천안).
- 질문 2: 첫 성공 기록은 프로젝트에 따로 보관합니다(브라우저가 아님). 저장 API는 보충 백엔드 phase가 만듭니다.
- 질문 3: ‘시험으로 돌아가기’ 단추(추천안).
- 7절 계약 빈칸(G01~G05)과 첫 사용 안내의 O3·O5는 화면 phase 전에 보충 백엔드 phase(Claude, 시험 먼저)로 채웁니다.
- 가장 큰 문제의 손실 점수는 채점기 식을 따릅니다: `무게 × (1 − 점수) / 무게 합 × 100`. 목표를 넘은 항목도 셉니다. 모든 항목의 손실을 더하면 `100 − 가중 종합`입니다.
- 갈래 2는 작업이 끝나도 그 항의 `results[항].ok`가 거짓이면 성공이 아닙니다.

아래는 승인 전의 질문과 선택지 기록입니다.

1. **문서 묶음을 바꾼 뒤 그 묶음의 실행이 없다면 무엇을 보여 줄까요?**
   - **해당 묶음의 결과 없음 표시 — 추천.** 장점: 전역 기준과 화면이 일치합니다. 단점: 이전 결과를 다시 고르는 이동이 필요합니다.
   - **이전 결과를 계속 표시.** 장점: 보던 내용을 유지합니다. 단점: 현재 묶음과 실행 당시 묶음이 달라집니다.
   - 추천 근거: 승인된 진단의 첫 과제는 점수와 시험의 입력 기준을 연결하는 것입니다.

2. **첫 성공 기록은 어디까지 유지할까요?**
   - **같은 브라우저에서 유지 — 추천.** 장점: 기존 저장 방식으로 구현할 수 있습니다. 단점: 브라우저 자료를 지우거나 바꾸면 기록이 사라집니다.
   - **프로젝트에 별도 보관.** 장점: 브라우저가 바뀌어도 유지할 수 있습니다. 단점: 기록 저장 계약과 사용자 구분이 추가로 필요합니다.
   - 추천 근거: 현재 제품은 로컬 앱입니다. 기존 안내도 브라우저 저장을 사용합니다.

3. **모델 준비가 끝나면 시험 화면으로 자동 이동할까요?**
   - **‘시험으로 돌아가기’를 표시 — 추천.** 장점: 다른 화면에서 읽던 작업을 끊지 않습니다. 단점: 한 번 눌러야 합니다.
   - **시험 화면으로 자동 이동.** 장점: 연결 직후 시험을 이어가기 쉽습니다. 단점: 15~25분 동안 시작한 다른 작업을 끊을 수 있습니다.
   - 추천 근거: 기다리는 동안 다른 화면을 쓸 수 있어야 합니다. 시험 대상은 두 안 모두 유지합니다.
