가장 큰 문제는 **점수의 기준과 다음 행동이 연결되지 않아, 사용자가 현재 상태를 이해하고 시험을 끝내기 어렵다는 점**입니다.

첨부 화면과 코드를 두 개의 독립 검토로 대조했습니다.
파일 변경과 앱 실행은 하지 않았습니다.
네트워크도 사용하지 않았습니다.
실행기 사전 확인이 경로 제한으로 막혀 PRODUCT.md와 DESIGN.md를 직접 읽었습니다.
두 문서는 현재 상태의 증거로만 사용했습니다.

아래의 ‘확인’은 화면 또는 정적 코드에서 확인했다는 뜻입니다.
실제 조작을 재현했다는 뜻은 아닙니다.

## 2. 새 구조가 반드시 풀어야 할 설계 과제

1. **문서 묶음과 채점용 답안을 모든 화면의 공통 기준으로 만들어야 합니다.**  
   점수를 본 자료와 시험할 자료가 조용히 달라지는 일을 막기 위해서입니다.

2. **점수마다 답안의 출처와 채점한 문서 수를 밝혀야 합니다.**  
   사람 검수 답안(골드)이 있는 3개 문서와 답안이 없는 `RAW-xx` 40개를 같은 숫자로 해석하면 안 되기 때문입니다.

3. **첫 성공의 첫 경로는 ‘현재 점수와 가장 큰 문제 이해’여야 합니다.**  
   모델 서버가 없어도 앱의 가치를 바로 확인해야 하기 때문입니다.

4. **첫 성공의 두 번째 경로는 ‘한 문서의 한 항 시험 후 결과 확인’이어야 합니다.**  
   연결이 없으면 모델 호출 없이 입력을 확인하는 연습(dry-run)으로 이어져야 하기 때문입니다.

5. **문제 확인에서 재시험까지 선택한 대상을 유지해야 합니다.**  
   문서와 항목을 다시 고르다가 다른 조건을 시험하는 일을 막기 위해서입니다.

6. **실행 전에 입력 자료의 사용 가능 여부를 확인해야 합니다.**  
   빈 폴더와 보호된 평가 문서를 서로 다른 상태로 설명해야 하기 때문입니다.

7. **모델 연결 준비를 시험 흐름 안에서 끝낼 수 있어야 합니다.**  
   이미 정한 기존 서버 재사용과 연결 관리 기능이 별도의 학습 과제가 되면 안 되기 때문입니다.

8. **서버의 소유 범위와 비용 상태를 조작 전에 보여 줘야 합니다.**  
   재시작 뒤 중복 생성과 다른 사람 서버의 삭제를 막기 위해서입니다.

9. **준비 중 상태와 실패 상태에 다음 행동을 붙여야 합니다.**  
   사용자가 긴 기다림과 복구 가능한 오류를 구분해야 하기 때문입니다.

10. **두 결과를 비교하기 전에 비교 조건이 맞는지 밝혀야 합니다.**  
    문서 구성의 차이와 반복 실행의 변동을 개선 효과로 오해하지 않게 하기 위해서입니다.

11. **핵심 결론을 먼저 보여 주되 모든 세부 정보는 찾아갈 수 있어야 합니다.**  
    정보 보존과 처음 온 사람의 이해를 함께 만족해야 하기 때문입니다.

12. **용어와 동작 이름을 화면 전체에서 일치시켜야 합니다.**

## 3. 지금 화면에서 살릴 만한 것

- **저장된 실행 결과를 서버 없이 보는 기능.** 첫 번째 성공 경로의 토대입니다.
- **큰 문제에서 원문으로 이동하는 연결.** 사용자의 질문과 직접 맞닿아 있습니다.
