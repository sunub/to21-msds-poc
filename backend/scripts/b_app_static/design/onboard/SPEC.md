# 처음 사용 안내를 Wispr Flow 구조로 다시 설계한다

작성: 2026-10-31, Claude, `first-use-guide` 참고 재현 + 설계만 범위. 제품 파일은 고치지 않았다. 상태: 시안 전 명세(승인 대기).

## 근거와 범위

이 명세의 근거는 세 가지다.

| 근거 | 쓰는 곳 |
|---|---|
| Wispr Flow 사례 파일(first-use-guide 스킬의 `references/cases/wispr-flow.md`, 2026-10-25 녹화 기반 기록) | 화면 순서, 챕터 구분, 진행 표시 방식, 상태 변화, 실습 구조, 웹앱 대응(좌우 분할) |
| 승인된 b_app 설계(`backend/scripts/b_app_static/design/STRUCTURE.md` "첫 사용 안내", `PRODUCT.md`, `DESIGN.md`) | 첫 성공 두 개의 정의, 성공 판정 규칙, 기록(journey v2), 자체 브랜드 색·글자 |
| 사용자 결정 2026-10-31 | 처음 사용 안내를 Wispr Flow 구조로 다시 설계한다. 승인 STRUCTURE의 "모달을 쓰지 않습니다"와 S08 화면은 이 관문에서 바뀐다 |

결과물은 자체 브랜드다. Wispr Flow의 로고, 영상, 그림, 글꼴 파일, 색(라벤더·주황·크림), 마케팅 문구는 쓰지 않는다. 구조와 동작만 가져온다. 사례 파일의 "출시물에서 바꿀 것" 표를 따른다: 화면 순서·챕터·진행 표시·위계(큰 제목, 주 버튼 하나)·상태 변화 시점은 유지하고, 색·글꼴·그림·문구는 b_app 것으로 바꾼다.

## 첫 실제 결과

- 갈래 1(서버 필요 없음): 최근 실행에서 가장 큰 문제 값 하나가 원문 몇 쪽 몇 번째 줄에서 왔는지 실제 자료로 본다. 성공 판정은 지금과 같다: AI가 댄 실제 근거 줄(추정 줄이 아님)이 선택되어 보인다(`evidence_line_shown`, `mismatch` 참).
- 갈래 2(AI 필요): 개발용 문서 한 부분을 실제 AI로 시험하고 결과를 본다. 성공 판정은 지금과 같다: `dry_run` 거짓, 결과 요청 200, `results[String(항)].ok` 참, 결과 요약 표시(`try_result_viewed`). AI 없이 보낼 내용만 확인하는 것은 "연습"으로 따로 센다.

바뀌는 것은 "어디서 하느냐"다. 지금은 안내가 사용자를 실제 화면(S02, S03)으로 보내고 띠로 따라간다. 새 안내는 Wispr Flow처럼 안내 화면 안의 실습 칸에서 실제 기능을 부르고 결과를 그 자리에서 보인다. 실제 화면은 "더 보기" 행동으로만 연다.

## 화면별 유지·변경·제거

Wispr Flow 화면 21개(W01~W21)를 기본으로 두고, b_app 안내 화면(G01~)에 대응시켰다. "출처"는 관찰(사례 파일 기록), 근거 문서(b_app 승인 설계), 신규 제안 중 하나다.

2. 안내는 비용이 드는 행동(서버 만들기, 모델 올리기, 터널 열기)을 대신 누르지 않는다. S06과 P02를 거친다.
3. 다른 화면에서 돌아온 것은 다시 조회할 계기일 뿐 성공이 아니다.
4. 새로고침하면 마지막 확정 단계로 돌아간다. 보내기는 자동으로 다시 하지 않는다. 준비 상태는 다시 조회한다.
5. 다시 보기는 진행만 처음으로 돌린다. 실제 성공 시각과 연습 횟수는 지우지 않는다.
